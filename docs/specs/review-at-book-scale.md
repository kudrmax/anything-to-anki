# Ревью коллекции размером с книгу

## Проблема

Любое действие в ревью перечитывает весь набор, и стоит это O(N) от числа его карточек:

- сервер собирает все карточки заново — 0,2 мс на карточку;
- по сети приходят все карточки целиком — 1,7 КБ на карточку;
- справа нарисован текст всех глав набора. Даже скрытая панель остаётся в разметке, она лишь сдвинута transform'ом, поэтому любое изменение размера на странице стоит 60 мс.

Замер на Worm: 27 тыс. карточек — 8 с до перехода фокуса и 46 МБ на нажатие. Вся книга даст около 80 тыс. карточек, это ~20 с. Даже если оставить только неизбежную часть (разделы и порядок), на 80 тыс. карточек получится ~2 с. Поэтому одной оптимизации кода мало.

## Принцип

Действие стоит столько, сколько карточек оно реально меняет, а не сколько их в наборе.

1. Раздел каждой карточки **хранится** и пересчитывается в момент, когда меняется то, от чего он зависит, и только у затронутых карточек. Правила разделов не меняются, меняется только момент расчёта.
2. Фронт получает и рисует только видимое: окно списка, текущую карточку и её главу.
3. Действия остаются синхронными: ничего не меняется на экране в случайный момент.

## Термины

- **Карточка** — фраза, которую показывает ревью (`phrases.shown_by` задан).
- **Открытый раздел** — Ready / Extra / Probably known: то, что возвращает `open_section`, независимо от того, разобрана ли карточка.
- **Разобрана** — `is_done` карточки: решение по ней или по её лемме в другом месте (Known-список, Learn в другом источнике, Learning в Anki).
- **Раздел** — Reviewed, если карточка разобрана, иначе её открытый раздел (`card_section`).
- **Знание** — всё, от чего зависят открытый раздел и признак «разобрана»:
  - списки Known и Unknown;
  - решения: Learn и Learning, в том числе в других источниках;
  - привязки Anki и их таймер (через 30 дней после экспорта слово считается Known);
  - порог частотности — одно значение для target'а (`FrequentWordThreshold`) и для остальных слов фразы (`frequent_zipf`), калибруется на каждом нажатии;
  - уровень пользователя.
- **Снимок** — порядок карточек на момент открытия ревью. Он и сейчас не меняется до перезагрузки (`keepLayout`). Новый дизайн это сохраняет.
- **Окно** — карточки снимка, данные которых загружены во фронт.

## Что хранится

### `card_sections`

| Колонка | Тип | Что это |
|---|---|---|
| `phrase_id` | int, PK, FK `phrases` (cascade) | карточка |
| `open_section` | text | открытый раздел |
| `is_done` | bool | разобрана ли |
| `new_word_count` | int | число новых слов фразы (`new_words`), ключ сортировки |
| `revision` | int | глобальный счётчик на момент последнего изменения строки |
| `removed` | bool | фраза перестала быть карточкой |

Раздел (`Reviewed`, если `is_done`, иначе `open_section`) вычисляется при чтении, а не хранится. Генерации Ready нужен открытый раздел и у разобранных карточек (`ReadyCards`), поэтому оба поля хранятся отдельно. Индексы: `(is_done, open_section)`, `(revision)`.

**Ревизии.** Каждая запись строки берёт следующее значение глобального счётчика `settings.sections_revision`. Строка меняется, только если новые значения отличаются от старых. Когда фраза перестаёт быть карточкой, строка не удаляется, а помечается `removed` с новой ревизией. Так `refresh` может отдать «что изменилось с ревизии `since`». Помеченные строки удаляются, когда удаляется сама фраза (cascade).

### `phrase_words`

| Колонка | Тип | Что это |
|---|---|---|
| `phrase_id` | int, FK `phrases` (cascade) | фраза |
| `lemma` | text, lower-case | лемма слова фразы кроме target'а; все слова, включая служебные: Unknown и Learning делают новым и служебное слово |
| `zipf` | float | частотность этого слова |

Индексы: `(lemma)`, `(zipf)`. Таблица отвечает на два вопроса: «в каких фразах есть лемма X» и «в каких фразах есть слово с частотой из полосы `[a, b)`». Строки есть у всех фраз, а не только у карточек: фраза может стать карточкой позже (`set_shown`).

### `settings.timers_checked_at`

Момент, до которого истёкшие таймеры Anki уже учтены. При заполнении таблиц ставится в момент заполнения.

## Когда пересчитывается

Пересчёт — правило `card_section`, применённое к выбранным карточкам. Пересчёт по лемме означает: все карточки этой леммы во всех источниках плюс все фразы из `phrase_words` с этой леммой.

### Изменилось знание

Подключение — в `UserVocabulary` и `DecisionEffects`: через них проходят все изменения знания. Пересчёт идёт в той же транзакции. Внутри `DecisionEffects.batch()` (экспорт) он делается один раз, в конце батча.

| Событие | Пересчёт |
|---|---|
| Решение по слову (Learn / Cloze / Known / Skip / отмена), включая снятие Known во всех источниках | по лемме |
| Правка списков Known и Unknown (настройки, bootstrap, report с `unknown_words`) | по каждой затронутой лемме |
| Синхронизация с Anki: новая привязка, освобождение | по каждой затронутой лемме |
| Порог частотности сменился с `a` на `b` | карточки, у которых zipf target'а в `[min(a,b), max(a,b))`, и фразы из `phrase_words` с zipf в этой полосе. Переход на «выключен» или с него — все карточки. Старый порог снимается до применения эффектов нажатия |
| Удаление источника | по каждой лемме его слов со статусом Learn (Cloze входит в него): в других источниках у этих лемм пропадает «Learn в другом месте». Леммы собираются до удаления, каскад их сотрёт. Learning не нужен: привязки Anki остаются. Удаление коллекции источники не удаляет, триггер ему не нужен |
| Истёк таймер Anki | по лемме; см. ниже |
| Смена уровня пользователя или настроек частотности | все карточки, синхронно в запросе настроек (~1–2 с на 80 тыс. карточек) |

**Таймеры.** Application-сервис `SectionsUpToDate` догоняет таймеры. Его явно вызывают use case'ы перед чтением разделов (ревью, `refresh`, экран источников, генерация); порт чтения ничего не пишет. Шаги:
1. выбирает привязки, у которых таймер истёк между `timers_checked_at` и текущим моментом (индекс `anki_synced_cards(learning_since)` с `released_at IS NULL`);
2. пересчитывает их леммы;
3. сдвигает `timers_checked_at`.

Если ничего не истекло, это один пустой запрос по индексу.

### Изменились карточки или фразы

Подключение — в методах порта `OccurrenceRepository`, а не в отдельных use case'ах: через них проходят все изменения набора карточек и текста фраз.

| Метод | Пересчёт |
|---|---|
| `add` | новая фраза: её `phrase_words`, и её строка, если она карточка |
| `write_text` (polish и его отмена, граница, правка фразы, замена примером, polish в воркере) | эта фраза: `phrase_words` и строка |
| `set_shown` | строки этих фраз появляются или удаляются |
| `apply_plan` (обработка, Update, Re-cut) | карточки и `phrase_words` затронутых источников |
| `set_earned_sections` (`fix-sections`) | эти карточки |

## Порты и use cases

- `CardSectionStore` (порт):
  - `write(rows)`, `mark_removed(phrase_ids)`;
  - `counts(scope)` — карточки по разделам набора;
  - `rows(scope)` — лёгкие строки для снимка;
  - `changed_since(scope, revision)` — строки набора с ревизией больше заданной;
  - `revision()` — текущее значение счётчика.
- `PhraseWordIndex` (порт): `write(phrase_id, words)`, `phrases_with_lemmas(lemmas)`, `phrases_with_zipf_in(a, b)`.
- `SectionRefresher` (application):
  - по набору карточек считает строки правилом `card_section` и пишет их;
  - возвращает затронутые карточки с новым разделом и `is_done`.

  Его вызывают все строки таблиц выше.
- `GetReviewUseCase` отдаёт шапку, снимок, его ревизию и окно вокруг нужной карточки.
- `RefreshReviewUseCase(scope, since, window_ids)` отдаёт:
  - данные карточек окна;
  - `changed_since(scope, since)`: id, раздел, `is_done`, `removed`;
  - новую ревизию и счётчики.

  Порядок всего набора он не строит, поэтому стоит O(изменений + окно).
- **Новые карточки** появляются в трёх местах. Добавление слова из текста и ручное добавление возвращают в своём ответе соседа новой карточки по текущему порядку. Карточки, появившиеся иначе (Rebuild, Update, Re-cut), приходят только после busy-операции, и тогда снимок строится заново.
- `GetReviewGenerationUseCase` берёт открытые разделы из `CardSectionStore`. Остальное, что он читает (`in_play` слов, задачи карточек), — тоже O(N). Сколько это стоит, выяснится замером на этапе 4: при необходимости это решается отдельно.

## Снимок

- **Как строится.** `rows(scope)` возвращает лёгкие строки: id фразы, id слова, раздел, `is_done`, `new_word_count` и ключи сортировки (`is_junk`, `is_phrasal_verb`, `frequency_band`, использование, CEFR, `occurrences`, zipf, позиция фразы). Порядок строится той же функцией `_grouped` с теми же ключами, что сейчас, только в Python, без сборки карточек целиком. Порядок не расходится с текущим.
- **Chronological.** Партиция «открытые / разобранные», ключ — позиция фразы. Страницы включаются и в этой сортировке: сейчас там `initially_shown_candidates=None`, то есть рисуется всё.
- **Что уходит на фронт.** Id, раздел и `is_done` каждой карточки и ревизия снимка: ~8 байт на карточку, ~0,6 МБ на 80 тыс. `is_done` нужен отдельно, потому что в chronological партиция — «открытые / разобранные».

## API

| Запрос | Что делает |
|---|---|
| `GET /api/review?scope&sort&around=<id>` | шапка, снимок, окно карточек вокруг `around` (или с начала) |
| `POST /api/review/refresh {scope, since, window_ids}` | то, что отдаёт `RefreshReviewUseCase` |
| `POST /api/review/cards {ids}` | данные карточек: «Show more», переход к карточке вне окна |
| `GET /api/review/documents?scope` | список глав: id источника и заголовок |
| `GET /api/review/documents/{source_id}` | текст одной главы и её подсветки с `phrase_id`, разделом и `is_done` |

## Фронт

Каждое действие, которое сейчас делает полную перезагрузку (`loadCandidates`), заменяется на `refresh`:

- нажатие;
- генерация meaning и TTS, перегенерация медиа, картинка;
- граница, polish и его отмена, правка фразы, report;
- добавление слова из текста.

Фронт хранит ревизию снимка и передаёт её как `since`; после каждого `refresh` она сдвигается. Изменения он применяет так же, как сейчас `keepLayout`:
- раздел у уже показанных карточек не меняется до перезагрузки, меняется только `is_done`;
- удалённые карточки убираются из снимка;
- новые встают за соседом, которого вернуло действие.

- **После нажатия.** `POST /decision`, затем `refresh`. Фокус переходит на следующую карточку снимка, у которой после `refresh` `is_done` ложно. Если её данных нет в окне, они загружаются.
- **Переход к карточке вне окна** (клик по слову в тексте, ссылка, prev/next). Загружается окно вокруг неё, а не все страницы до неё.
- **Busy-операции** (Rebuild, Update, Re-cut). Пока идёт операция — `refresh` раз в интервал. Когда операция закончилась — снимок строится заново: id фраз могли смениться.
- **Опрос во время генерации** — тоже `refresh`. Новый опрос не стартует, пока не закончился предыдущий.
- **Текст справа.** Загружена и нарисована только глава текущей карточки. Остальные главы — свёрнутые заголовки, текст подгружается при раскрытии. Скрытая панель убирается из разметки. Глава перечитывается после `refresh`, если в изменениях есть её карточки. Это меняет интерфейс, поэтому до реализации — скриншоты.

## Корректность

- **Инвариант.** После любой операции `card_sections` совпадает с полным пересчётом по `card_section`. Тест прогоняет случайные последовательности операций из таблиц выше: решения, правки списков, синхронизацию, удаление источника, сдвиг порога, таймер, правки фраз, Re-cut. После каждой операции он сравнивает хранимое с полным пересчётом.
- **Полный пересчёт** — команда make по образцу `fix-sections`, на случай расхождения.
- **Миграция.** Alembic создаёт таблицы. Заполнение — полный пересчёт при первом запуске, по образцу `fix-sections`: `card_sections` для всех карточек, `phrase_words` для всех фраз.

## Ожидаемый результат

- **Нажатие:** решение, пересчёт затронутых карточек, окно (~15 карточек) и один подсчёт. Десятки миллисекунд независимо от размера набора; до сотен — для частой леммы.
- **Открытие ревью:** лёгкие строки и сортировка. Цель — меньше 1 с на 80 тыс. карточек, проверить замером.
- **Экран источников и `/review/generation`:** берут данные из `CardSectionStore`.

## Этапы

1. Таблицы, `SectionRefresher`, все триггеры, тест инварианта, команда полного пересчёта.
2. Снимок, окно, `refresh`, счётчики; фронт списка и всех действий; chronological со страницами.
3. Текст справа по главам — после согласования скриншотов.
4. Опрос во время генерации, `/review/generation`, экран источников.

Каждый этап замеряется на копиях с Worm: 25, 100 и 150 глав.
