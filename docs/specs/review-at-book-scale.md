# Ревью коллекции размером с книгу

## Проблема

Каждое действие в ревью пересчитывает и передаёт весь набор карточек, а фронт рисует текст всех глав. На всём Worm (121 тыс. карточек) нажатие стоит ~20 с, открытие ревью — ~25 с. Время растёт линейно с размером набора.

Чтобы нажатие стоило миллисекунды, состояние карточек (раздел, разобрана ли) нужно хранить готовым и пересчитывать только у затронутых карточек. Это надёжно, только если данные устроены правильно. Сейчас в трёх местах они нарушают принципы.

## Основа: модель статусов от 19.10.2026

Модель «слово / фраза / показана» и факты решений согласованы раньше (`words-phrases-rebuild.md`, коммит `c1768fff`) и не меняются:

- **Слово** (`candidates`) — лемма в источнике и её факты: CEFR, частота, usage, число вхождений.
- **Фраза** (`phrases`) — место в тексте (блок, строка, символ) и всё, что к нему относится: текст, выбор на карточке, перевод, озвучка, правки. Rebuild обновляет фразу на том же месте, а не пересоздаёт (`rebuild_plan_writer.py:73–150`). Поэтому всё это правильно живёт на фразе.
- **Показана** — отметка на фразе (`shown_by`): какая фраза у слова стала карточкой.
- **Факты знания:**
  - выбор на карточке (Learn, Cloze, Known, Skip) — живёт и умирает с карточкой;
  - Known и Unknown — про лемму, переживают источник;
  - привязка к Anki — история экспорта.
- **Статус слова вычисляется** из этих фактов. Отдельная таблица статуса была бы копией.

## Решения

### 1. Статусы — пять взаимоисключающих (Макс, 21.10.2026)

Статусы: `нет`, `учу`, `в Anki`, `знаю`, `не знаю`. Переходы:
- нажатие Learn, Cloze или Known снимает «не знаю»;
- отметка «не знаю» снимает «знаю» и решение «учу».

Это заменяет правило 19.10 «Unknown сильнее всего», по которому Unknown мог стоять рядом с Learn.

### 2. Таблицы: три исправления

| Сейчас | Нарушение | Станет |
|---|---|---|
| `candidates.status` | хранимая копия вычисляемого статуса; держит в согласии отдельный писатель (`sqla_word_state_repository.py:92`) | удаляется; статус живёт только в проекции, туда переходят 13 читателей |
| `known_words`, `unknown_words` | две таблицы для взаимоисключающих отметок; исключение держит код | одна таблица `word_marks(lemma PK, mark known/unknown, pos_list, created_at)`; исключение гарантирует схема |
| `anki_synced_cards.card_choice` | зеркало выбора карточки, переписывается при каждом сохранении слова (`sqla_word_state_repository.py:77–88`) | записывается один раз, когда карточка или источник исчезают: это факт «каким было решение в момент исчезновения» (`decision_rules.py:549`) |

`phrases` и `candidates` не делятся: каждая хранит факты одной сущности, а раздел добавил бы соединений и миграций без новой гарантии.

### 3. Принципы

1. **Один писатель у каждого факта.**
   - Выбор на карточке пишет только репозиторий состояния слова.
   - Текст и показ фразы — только репозиторий фраз; запись Rebuild — его внутренняя часть.
   - Слово — только репозиторий слов.
   - Отметки — только `UserVocabulary`.
   - Привязки — только репозиторий Anki.
2. **Вычисляемое — только в проекции.** Её можно стереть и посчитать заново без потерь.
3. **Транзакция — только через `SqlaUnitOfWork`.** Он уже есть в проекте. 66 прямых `commit()` в 25 файлах переходят на него.
4. **Правила — только в domain.** SQL выбирает и сортирует готовые значения, фронт ничего не вычисляет.
5. **Время меняет состояние явной записью.** Время берётся через порт `Clock`, он уже есть.

### 4. Как проекция узнаёт об изменениях — явные события

Репозиторий-владелец, записывая факт, добавляет в Unit of Work событие:

| Событие | Кто создаёт |
|---|---|
| `WordDecisionChanged(lemma)` | репозиторий состояния слова |
| `PhraseChanged(phrase_id)` | репозиторий фраз (текст, показ, создание, удаление) |
| `WordsChanged(source_id, lemmas)` | репозиторий слов (Rebuild, удаление) |
| `MarkChanged(lemma)` | `UserVocabulary` |
| `BindingChanged(lemma)` | репозиторий Anki |
| `LevelChanged` | настройки |

Перед коммитом Unit of Work передаёт события проектору `CardStateProjector` (application). Проектор пересчитывает затронутые карточки правилами domain. Данные и проекция коммитятся вместе, поэтому ответ на нажатие уже содержит новые разделы.

**Почему явные события, а не другие способы:**
- Триггеры базы держат логику в БД и ломают миграции.
- Чтение списка изменённых объектов из сессии SQLAlchemy неявно и не видит массовых запросов Rebuild.
- Явное событие видно в коде, и после принципа 1 мест, где оно создаётся, немного: по одному на метод записи владельца.

## Проекция

| Таблица | Что хранит |
|---|---|
| `word_states` | `word_id`, статус слова (бывший `candidates.status`) |
| `card_states` | `phrase_id`, `source_id`, `word_id`, `lemma`, `is_done`, `wants_generation`; раздел при каждом из 8 шагов порога; число новых слов при каждом шаге; ключи сортировки; `changes_at` — когда состояние изменится по времени; `revision` |
| `phrase_words` | леммы каждой фразы-карточки; индекс «в каких фразах стоит лемма» |

- **Порог** принимает одно из 8 значений (`THRESHOLD_STEPS`: 2.5 … 5.5 или «выключен»). Раздел хранится для каждого, поэтому сдвиг порога ничего не пересчитывает.
- **Время.** Воркер раз в минуту обычной транзакцией пересчитывает карточки с `changes_at <= now`: например, слово через 30 дней в Anki стало «знаю». Чтение ничего не пишет.
- **Пересборка с нуля** — при каждом запуске приложения, до приёма запросов (~4 с на всю книгу). Покрывает смену правил и миграции. Если какой-то баг проскочил тесты, после перезапуска состояние снова верное.

## Гарантии

1. **Дифференциальный тест** в `make test`. Случайные сценарии реальных use case'ов: решения и отмены, отметки, экспорт и снятие привязки, удаление источника, Rebuild, Re-cut, правки, смена уровня, сдвиг часов. Сценарии включают общие леммы в разных источниках. После каждого шага проекция совпадает с полным расчётом: разделы, счётчики, порядок каждой сортировки.
2. **Тест владельцев:** запись в модель таблицы есть только в модуле её владельца.
3. **Тест пути коммита:** `commit()` и `sessionmaker(` есть только в `SqlaUnitOfWork` и `database.py`.
4. **Пересборка при каждом запуске.**
5. **`make card-states-check`** — для разработчика: показывает расхождения проекции с полным расчётом, ничего не исправляя.

`make test` обязателен перед каждым вливанием, поэтому ошибка пересчёта не доходит до master.

## API и фронт

- **Сервер хранит порядок открытого ревью** в памяти: id, раздел и `is_done` на момент открытия. Сейчас этот порядок держит фронт (`keepLayout`). После перезапуска сервер отвечает «перезагрузить порядок», и это стоит ~0,25 с.
- **Сервер отдаёт:**
  - окно карточек: показанные страницы плюс текущая карточка с соседями;
  - изменения с ревизии клиента;
  - следующую карточку для фокуса (нынешнее правило `nextFocus`);
  - место новых карточек;
  - шапку: прогресс, статус, `busy`, «AI недоступен».
- **Фронт только показывает.** Все действия идут через одну обёртку `mutate → refresh`.
- **Текст справа** загружается по главам.

## Миграция данных

- Alembic убирает `candidates.status`, сливает `known_words` и `unknown_words` в `word_marks`, создаёт таблицы проекции.
- **Конфликты по правилу 1:** лемма одновременно в Unknown и с решением, или в Known и в Unknown, или два решения по лемме, оставшиеся со времён до правила `P6`. Скрипт решает их общим правилом «позднее действие побеждает» по времени действия. Каждое изменение пишется в лог миграции. Разрешено Максом 21.10.2026.
- Проверка — на копии dev-базы и на копии с Worm.

## Этапы

Каждый этап — своя ветка, все существующие тесты зелёные.

1. `SqlaUnitOfWork` — единственный путь коммита; тест пути коммита.
2. Один писатель у каждого факта; тест владельцев.
3. Domain: `THRESHOLD_STEPS`, новизна слова без порога, раздел при каждом шаге; правило пяти статусов.
4. Таблицы: `word_marks`, удаление `candidates.status`, `card_choice` как факт исчезновения; миграция с конфликтами.
5. Проекция, события, воркер времени, пересборка при запуске, дифференциальный тест, `make card-states-check`.
6. API и фронт ревью.
7. Текст справа по главам.
