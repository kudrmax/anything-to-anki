# Ревью коллекции размером с книгу

## Проблема

Каждое действие в ревью перечитывает весь набор. Сервер пересчитывает и собирает все карточки, сеть передаёт их целиком, фронт рисует текст всех глав.

На всём Worm (305 глав, 121 тыс. карточек) нажатие стоит ~20 с, открытие ревью — ~25 с. Время растёт линейно с размером набора.

## Решение

1. Состояние каждой карточки (разобрана ли, раздел при каждом пороге) **хранится** и пересчитывается только у тех карточек, которых касается изменение.
2. Что устарело, отмечает **сама база** триггерами SQLite на входных таблицах. Код приложения о них не знает и забыть не может. Перед чтением хранимого отмеченное досчитывается.
3. Фронт получает и рисует только видимое: окно карточек и главу текста.

Правила разделов остаются в domain, одной реализацией. Хранимое — это их результат, кэш, который всегда можно пересчитать с нуля.

## Термины

- **Карточка** — фраза, которую показывает ревью (`phrases.shown_by` задан).
- **Порог** — порог частотности: одно из 8 значений `THRESHOLD_STEPS` (2.5, 3.0, …, 5.5, «выключен»).
- **Новизна слова** (`Newness`) — правило `is_new`, разложенное без порога:
  - `ALWAYS` — слово в Unknown, изучается или ждёт экспорта как Learn;
  - `IF_RARE` — содержательное, выше уровня и не в Known: новое, если реже порога;
  - `NEVER` — не новое.
- **Входы** — всё, из чего считается состояние карточки:
  - фразы и их показ;
  - слова (`candidates`);
  - списки Known и Unknown;
  - привязки Anki;
  - ключ `cefr_level` в `settings`;
  - время (только таймер Anki).

  Инвариант: **все входы лежат в БД**, кроме часов.
- **Грязное** — лемма или фраза, у которой изменился вход, а хранимое ещё не пересчитано.
- **Снимок** — порядок карточек на момент открытия ревью. Как и сейчас (`keepLayout`), он не перестраивается до перезагрузки.

## Схема

```
запись во входную таблицу (любой код, любой процесс)
        │  триггер SQLite, в той же транзакции
        ▼
 dirty_lemmas / dirty_phrases
        │  CardStateProjection.current() — в начале use case'а чтения,
        │  и воркер в конце каждой задачи
        ▼
 phrase_words (newness)  ─►  card_states (is_done, разделы ×8)
        │
        ▼
 CurrentCardStates: счётчики, снимок, окно — в той же транзакции
```

## Domain

- `THRESHOLD_STEPS` и `step_index(threshold)`. Калибратор и ручные ключи порога берут шаги отсюда. Порог вне набора — ошибка.
- `newness(word, vocabulary, user_level) -> Newness`. `is_new` выражается через неё.
- `PhraseNewness.of(words: Iterable[(lemma, zipf, newness)])` — число новых слов фразы (разных лемм) для каждого шага.
- `section_of`, `open_section` и сортировки выражаются через `PhraseNewness` и Protocol `SortFacts`. Ни одна формула не повторяется ни в SQL, ни во фронте.
- `progress()` и `reach()` принимают счётчики по разделам, а не список разделов.

## Хранимое

### `phrase_words` — слова фраз-карточек

| Колонка | Что это |
|---|---|
| `phrase_id`, `position`, `lemma` | PK `(phrase_id, position)`, `WITHOUT ROWID`; `position` — номер слова во фразе |
| `zipf`, `content`, `level` | факты слова из текста фразы |
| `newness` | класс сейчас |

Индекс `(lemma)`. Строки есть только у карточек.

### `card_states` — состояние карточки

| Колонка | Что это |
|---|---|
| `phrase_id` | PK. Без FK-каскада: удаление видит досчёт и пишет `card_removals` |
| `source_id`, `word_id` | отбор по набору и группировка по слову |
| `is_done`, `wants_generation` | из `card_view` |
| `open_sections` | 8 букв: открытый раздел при каждом шаге (`PhraseNewness` + `open_section`) |
| `new_counts` | 8 чисел для сортировки |
| `revision` | номер последнего изменения строки |

Индексы: `(source_id, revision)`, покрывающий `(source_id, is_done, open_sections)`, `(word_id)`. Раздел карточки — `section(is_done, open)` из domain; SQL лишь выбирает букву по `step_index` и группирует.

Почему отдельная таблица, а не колонки `phrases`: триггер на `phrases` реагирует на любое изменение строки, без списка «входных» колонок, а запись состояния не запускает сама себя.

### Служебные

- `dirty_lemmas(lemma)` и `dirty_phrases(phrase_id)` — без UNIQUE, дубли схлопывает досчёт.
- `card_removals(phrase_id, revision)` — хранится 7 дней. При полном пересчёте исчезнувшие карточки тоже пишутся сюда. Отдельно хранится `card_removals_floor` — ревизия самой старой хранимой записи: при `since < floor` ответ — `snapshot_stale`.
- В `settings` (собственные ключи, не входы):
  - `card_states_revision`;
  - `card_states_rules` — отпечаток правил;
  - `card_states_timers_at`;
  - `card_states_all_dirty`;
- `card_removals_floor`.

## Триггеры

Все определения — в одном модуле infrastructure: `CARD_STATE_TRIGGERS`, `create_all()`, `drop_all()`. Все леммы — `lower()`.

| Таблица | INSERT / UPDATE / DELETE отмечает |
|---|---|
| `phrases` | `NEW.id` и `OLD.id`; леммы слов `OLD.candidate_id` и `NEW.candidate_id` (через `candidates`) |
| `candidates` | `OLD.lemma`, `NEW.lemma`; фразы этого слова (одного источника, единицы штук) — факты target'а (`pos`, `zipf`) меняются на месте |
| `known_words`, `unknown_words` | `OLD.lemma`, `NEW.lemma` |
| `anki_synced_cards` | `OLD.lemma`, `NEW.lemma` по собственной колонке: `phrase_id` бывает NULL после удаления источника |
| `settings` `WHEN key IN ('cefr_level')` | `card_states_all_dirty` |

Каскадные удаления и `SET NULL` запускают триггеры дочерних таблиц; это проверено. От REPLACE защищает `PRAGMA recursive_triggers=ON`.

**Миграции.** Хук в `env.py` срабатывает, только когда upgrade до head действительно применяет миграции. Если ревизия Alembic не изменилась, он ничего не делает. Порядок в той же транзакции:
1. перед миграциями — `drop_all()`;
2. после — `create_all()` и `all_dirty`.

Batch-пересоздание таблиц не ломается и не теряет триггеры, и ни одной миграции не нужно о них помнить. При downgrade хук триггеры не создаёт.

При старте набор триггеров в `sqlite_master` сверяется с `CARD_STATE_TRIGGERS`. При расхождении — ошибка в лог, `create_all()` и `all_dirty`.

`PRAGMA recursive_triggers=ON` действует на одно соединение. Поэтому он ставится в `connect`-листенере общей функции создания engine в `database.py`, через которую соединяются app, воркер, `env.py` и make-команды. Тест проверяет прагму на соединении каждого из этих путей.

## Досчёт: `CardStateProjection.current()`

Application-сервис, единственная дверь к хранимому. Порт `CardStateStore` внедряется только в него, что проверяет архитектурный тест. `current()` вызывается один раз за use case и возвращает `CurrentCardStates`: прочитать хранимое в обход досчёта нельзя на уровне типов.

0. **Отпечаток правил** сверяется с сохранённым при каждом вызове, включая быстрый путь: это одна строка `settings`. Если он не совпал, процесс работает со старым кодом. Он ничего не пишет, пишет в лог ERROR и отвечает ошибкой. Так старый воркер, доживающий после деплоя, не запишет состояния по старым правилам. Кроме того, `make up` останавливает воркер до старта app.
1. **Быстрый путь.** Если очереди пусты, флаг снят и истёкших таймеров нет, досчёт не нужен и запись не берётся. Проверка и чтение идут в одной транзакции чтения WAL. Для таймеров есть индекс по `anki_synced_cards(learning_since)` с `released_at IS NULL`.
2. Иначе транзакция чтения закрывается: WAL-чтение нельзя повысить до записи, получится `SQLITE_BUSY_SNAPSHOT`. Затем — `uow.write()` (`BEGIN IMMEDIATE`) со свежим `now` от часов. Если часы откатились (`now < timers_at`), для таймеров берётся `timers_at`, в лог пишется warning, досчёт идёт дальше.
3. **Полный пересчёт** (~4 с на 121 тыс.), если:
   - стоит `all_dirty`;
   - отпечаток правил не совпал;
   - досчёт затронет больше 10% карточек. Объём = `COUNT(DISTINCT phrase_id)` по грязным фразам и по `phrase_words` грязных лемм.

   Ревизию при полном пересчёте получают только строки, которые реально изменились. Открытый снимок не получит весь набор как «изменения».
4. **Таймеры.** Леммы, чей таймер истёк в `(timers_at, now]`, становятся грязными. Граница — `known_on` из domain. Затем `timers_at = now`.
5. **Грязные фразы.** Перечитываются, переписываются `phrase_words` и строка. Фразы, которой нет или которая не карточка, — строка удаляется и пишется в `card_removals`.
6. **Грязные леммы.**
   - `newness` пересчитывается правилом из domain по сочетаниям `content × level` этой леммы;
   - `is_done` и `wants_generation` пересчитываются у её карточек;
   - у фраз, где она встречается, `PhraseNewness` и `open_sections` собираются в Python из `phrase_words`.
7. Изменившимся строкам — новая ревизия. Очередь очищается в той же транзакции: под `BEGIN IMMEDIATE` других писателей нет.
8. Чтение — в той же транзакции.

Полный пересчёт после деплоя и миграций делает при старте только app (`make up`), а не первый GET и не воркер. Смена уровня делает его в запросе настроек; на экране лоадер.

Воркер в конце каждой задачи вызывает `current()` короткой транзакцией. Очередь не копится, а ревью не платит за чужую работу.

Журнал — WAL, `synchronous=NORMAL`: чтение не ждёт писателя.

**Отпечаток правил** — порт `RulesFingerprint`, реализация в infrastructure. Это хеш всех `backend/src/backend/**/*.py` и головы Alembic. Любой деплой кода — полный пересчёт при старте.

## Чтение и API

| Запрос | Ответ |
|---|---|
| `GET /api/review?scope&sort&around` | шапка; снимок (id, раздел, `is_done`) и его ревизия; окно; начальный фокус — его выбирает backend |
| `POST /api/review/refresh {scope, since, window_ids, pressed_id?}` | шапка; изменения с `since` (см. ниже); окно; `next_focus_id`; `snapshot_stale` |
| `POST /api/review/cards {ids}` | полные данные карточек |
| `GET /api/review/documents?scope` | список глав |
| `GET /api/review/documents/{source_id}` | текст главы и подсветки (`phrase_id`, `is_done`) |

**Изменения с `since`.** Это строки набора с `revision > since`:
- уже бывшие в снимке — только `is_done`; раздел в снимке не меняется до перезагрузки, как сейчас;
- новые — с `after_id`: за какой карточкой текущего порядка их вставить;
- удалённые — из `card_removals`;
- `changed_sources` — главы, у которых сменились подсветки.

**Шапка** — то же, что сейчас в `ReviewDTO`:
- `progress` из счётчиков;
- `learn_count`, `status`, `busy`;
- `ai_unavailable` — флаг VPN считает backend по всему набору.

**`snapshot_stale`** — снимок пора перестроить: busy-операция закончилась (Rebuild, Update, Re-cut) или `since` старше хранимых удалений.

**`next_focus_id`** вычисляет backend по нынешнему правилу `nextFocus`:
- фокус уходит, только если нажатая карточка стала разобранной;
- ищется внутри её раздела (в chronological — без раздела), сначала ниже, потом сначала;
- данные этой карточки приходят в окне того же ответа.

**Окно** — показанный префикс списка (страницы, как «Show more») плюс текущая карточка с соседями ±N. Данные окна каждый раз перечитываются целиком: meaning, медиа и задачи не входят в `card_states`.

Chronological сортирует backend и замораживает так же, как остальные сортировки.

## Фронт

- Одна обёртка `mutate → refresh` для всех действий, без ручных вызовов перезагрузки.
- Фронт применяет ответ и ничего не вычисляет:
  - снимок и изменения;
  - фокус;
  - шапку;
  - перечитывание глав из `changed_sources`.
- `currentId` меняется после того, как данные карточки в окне. От этого зависят карточка, хоткеи, автоаудио и скролл текста.
- Опрос не стартует, пока не закончился предыдущий.
- Текст справа: глава текущей карточки и глава правки границы. Скрытая панель убирается из разметки, позиция прокрутки восстанавливается.

## Гарантии

1. **Триггеры на месте:** сверка при старте и тест «`alembic upgrade head` → набор триггеров = эталон».
2. **Структурный тест входов.**
   - База собирается из Alembic, кэши выключены.
   - Фикстура проходит все ветки правил: все строки `STANDING` и `PRESSED`, привязки, отсутствующий `cefr_level`.
   - Перехват SQL: каждая прочитанная таблица и каждый ключ `settings`, кроме собственных, обязаны быть под триггером.
   - Досчёт не читает ничего вне БД, кроме порта часов.
3. **Точечные тесты триггеров:** CASCADE, SET NULL, регистр, удаление источника и затем освобождение привязки.
4. **Дифференциальный тест.**
   - `hypothesis` `RuleBasedStateMachine`, фиксированный seed, 2–3 источника, < 10 с.
   - Операции — реальные use case'ы: решения и отмены, Known и Unknown, синхронизация, удаление источника, `write_data` при Rebuild, polish и его отмена, граница, Re-cut, смена уровня, сдвиг часов через таймер, два соединения вперемешку.
   - Эталон — нынешний живой путь (`ReviewCards` + `KnowledgeScope` + `card_section`). Он остаётся в коде как `LiveCardStates`.
   - Сравниваются состояния, счётчики и порядок снимка во всех трёх сортировках.
5. **Проверка в работе.** `make card-states-check` выводит diff хранимого с `LiveCardStates`, ничего не исправляя. В dev каждый `refresh` сверяет строки окна с `LiveCardStates` с тем же `now`, что и досчёт, и пишет ERROR в `make logs`. `current()` логирует, сколько обработал и за сколько.
6. **В `CLAUDE.md`** раздел «Хранимое состояние карточек»:
   1. новый вход — только в БД;
   2. триггер — через модуль триггеров;
   3. проверка — `make card-states-check`;
   4. писать в `card_states` и `dirty_*` в обход проекции нельзя.

## Замеры прототипа (весь Worm, 121 тыс. карточек)

| | Сейчас | С решением |
|---|---|---|
| Досчёт после нажатия, 99% слов (≤ 184 карточек) | ~20 с на всё | 11–30 мс |
| Досчёт для самых частых слов книги (до 2558 карточек) | ~20 с | до ~130 мс |
| Само решение (`decide`), без изменений | ~20 мс | ~20 мс |
| Счётчики (`GROUP BY`) | — | 26 мс |
| Открытие: снимок и сортировка | ~25 с | ~0,25 с |
| Полный пересчёт | — | ~4 с |
| Рост базы | 173 МБ | 239 МБ (+38%) |
| Триггер на запись `phrases` | — | +0,5 мкс на строку |

Совпадение с текущим правилом: 0 расхождений на 121 тыс. карточек после 11 настоящих нажатий, включая самые тяжёлые слова.

При реализации домерить:
- холодный кэш;
- ожидание блокировки при параллельном Rebuild;
- p95;
- досчёт после Rebuild всей книги;
- триггеры с подзапросом в `candidates`;
- удаление книги целиком: 121 тыс. срабатываний DELETE-триггеров;
- как часто генерация и картинки пишут в `phrases`.

## Этапы

1. Domain: `THRESHOLD_STEPS`, `Newness`, `PhraseNewness`, `SortFacts`. Через них переписаны `is_new`, `section_of` и сортировки без изменения поведения.
2. Хранимое: таблицы, триггеры, хук в `env.py`, WAL, `CardStateProjection`, `LiveCardStates`, все тесты из «Гарантий», `make card-states-check`.
3. Чтение и API: шапка, снимок, окно, `refresh`, `next_focus_id`, экран источников, обзор генерации.
4. Фронт: обёртка `mutate → refresh`, окно, загрузка карточки перед фокусом.
5. Текст справа по главам — после скриншотов.

Каждый этап замеряется на копиях с Worm (25 глав и вся книга).
