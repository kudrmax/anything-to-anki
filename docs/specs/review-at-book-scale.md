# Ревью коллекции размером с книгу

## Проблема

Каждое действие в ревью пересчитывает и передаёт весь набор, а фронт рисует текст всех глав. На всём Worm (121 тыс. карточек) нажатие стоит ~20 с, открытие ревью — ~25 с. Время растёт линейно с размером набора.

Ускорить можно, только если хранить готовое состояние карточек (раздел, разобрана ли) и обновлять его точечно. Чтобы это было надёжно, сначала нужно навести порядок в данных. Сейчас знание о слове разбросано по четырём таблицам, в одних строках смешаны разные ответственности, у таблиц по нескольку писателей.

## Принципы

1. **Одна таблица — одна ответственность — один владелец.** В таблицу пишет и из неё удаляет только её репозиторий.
2. **Исходные данные отдельно от вычисляемых.**
   - Исходные — то, что нельзя восстановить: тексты, решения, статусы слов.
   - Вычисляемые — то, что считается из исходных: раздел карточки, разобрана ли она. Их хранит **materialized view** (материализованное представление): таблица с готовым результатом, которую можно стереть и посчитать заново.
3. **Транзакция — только через Unit of Work.** Он уже есть в проекте (`SqlaUnitOfWork`). Прямых `session.commit()` больше нет. Перед коммитом Unit of Work обновляет materialized view по изменениям этой транзакции, и данные с представлением коммитятся вместе.
4. **Правила только в domain.** SQL и фронт правил не содержат.
5. **Время — обычная колонка.** Если статус изменится сам со временем, момент изменения хранится колонкой. Текущее время код берёт только через порт `Clock`, он уже есть.

## Сущности

- **Слово** — лемма, которую анализ нашёл в источнике, с фактами: часть речи, частота, CEFR, число вхождений.
- **Фраза** — кусок текста источника вокруг слова. У слова их может быть несколько.
- **Карточка** — фраза, которую ревью показывает для слова, и то, что пользователь сделал с ней: Skip, вариант Cloze, правки текста.
- **Статус слова** — что пользователь знает о лемме, одно на все источники:
  - нет строки — слово ещё не трогали;
  - `learn` — нажал Learn или Cloze, ещё не в Anki;
  - `learning` — в Anki, есть момент экспорта;
  - `known` — нажал Known, добавил в список или прошло 30 дней в Anki;
  - `unknown` — сказал «не знаю».
- **Заметка Anki** — привязка карточки к заметке в Anki.

Статус слова — исходные данные, а не вычисляемые. У леммы не может быть двух решений: нажатие на карточку слова, решённого в другом источнике, отклоняется (`decision_rules.py:315`, `P6`). Отмена возвращает слово в «нет строки».

**Что это упрощает.**
- Знание о слове читается из одного места, а не собирается из четырёх.
- Правило «позднее действие побеждает» (Q15, сейчас разбросано по `card_choice.py:204`, `card_view.py:252`, `decision_rules.py:420`) становится обычной записью статуса.
- Rebuild меняет только `words` и `phrases` и не может задеть решения пользователя.
- Статус слова не зависит от источника: удаление источника не трогает знание.

### Materialized view (владелец — `CardStateView`)

**`card_states`** — одна строка на карточку.

| Колонка | Что это |
|---|---|
| `card_id`, `source_id`, `word_id`, `lemma` | |
| `is_done`, `wants_generation` | из `card_view` |
| `sections` | раздел при каждом из 8 шагов порога (`THRESHOLD_STEPS`) |
| `new_counts` | число новых слов фразы при каждом шаге, для сортировки |
| `valid_until` | ближайший `known_at` среди лемм карточки: когда её состояние изменится само |
| `revision` | для обновления окна на фронте |

**`phrase_words`** — какие леммы стоят в каждой фразе-карточке: `card_id`, `position`, `lemma`, `zipf`, `content`, `level`. Нужна, чтобы найти карточки, которых касается смена статуса слова.

Порог выбирает колонку при чтении, поэтому его сдвиг ничего не пересчитывает.

## Как обновляется materialized view

- Владелец исходной таблицы при записи сообщает Unit of Work, что изменилось:
  - статус слова — лемму;
  - фраза или карточка — её id;
  - анализ источника — источник;
  - уровень пользователя — «всё».
- Перед коммитом Unit of Work пересчитывает затронутые карточки правилами domain и пишет `card_states`.
- Перед чтением ревью пересчитываются карточки с `valid_until <= now`.
- При старте приложения представление пересобирается с нуля: ~4 с на всю книгу. Так покрываются смена правил и миграции. Расхождение старого и нового — ERROR в `make logs`.
- Журнал SQLite — WAL, чтобы чтение не блокировало запись.

## Чем гарантируется

Тесты проверяют принципы:

1. Модель таблицы импортирует только её владелец.
2. `commit()` и `sessionmaker(` встречаются только в Unit of Work и `database.py`.
3. Между таблицами разных владельцев нет `ON DELETE CASCADE`: удаление идёт через владельца.
4. Каждая изменённая строка исходных таблиц сопровождается сообщением владельца. В тестовой базе это проверяют триггеры-журналы; в рабочей базе их нет.
5. Полный расчёт читает ровно объявленные исходные таблицы.
6. Дифференциальный тест: случайные сценарии реальных use case'ов, после каждого materialized view совпадает с полным расчётом — разделы, счётчики, порядок каждой сортировки.

## Миграция данных

- Alembic раскладывает старые таблицы по новым.
- Конфликты — у одной леммы больше одного решения, оставшиеся со времён до правила `P6`, — решаются общим правилом «позднее действие побеждает». Это то же правило Q15, по `decided_at`. Остальные решения снимаются, каждое пишется в лог миграции.
- Проверка на копии dev-базы и на копии с Worm. Prod обновляется обычным `make up`.

## API и фронт

Сервер хранит порядок карточек открытого ревью (сейчас его держит фронт в `keepLayout`) и отдаёт:
- окно карточек;
- изменения с ревизии клиента;
- следующую карточку для фокуса;
- место новых карточек;
- шапку.

Фронт только показывает. Все действия идут через одну обёртку `mutate → refresh`. Текст справа загружается по главам.

Прототип совпал с текущим правилом на 121 тыс. карточек после 11 настоящих нажатий, расхождений 0.

## Этапы

Каждый этап — своя ветка, все существующие тесты зелёные, поведение не меняется до этапа 5.

1. Unit of Work — единственный путь коммита (66 вызовов в 25 файлах).
2. Domain: `THRESHOLD_STEPS`, правило новизны слова без порога, раздел при каждом шаге.
3. Таблицы: `words`, `phrases`, `cards`, `word_statuses`, `anki_notes`; миграция данных со снятием конфликтов; тесты 1–3.
4. Materialized view, тесты 4–6.
5. API и фронт ревью.
6. Текст справа по главам.
