# Ревью коллекции размером с книгу

## Проблема

Каждое действие в ревью перечитывает весь набор: сервер заново считает и собирает все карточки, сеть передаёт их целиком, фронт рисует текст всех глав. На всём Worm (121 тыс. карточек) нажатие стоит ~20 с, открытие ревью — ~25 с. Время растёт линейно с набором.

## Решение

Обычный паттерн для производных данных: **read model** (проекция), которая обновляется через **transactional outbox**.

1. **Источник правды** не меняется: фразы, слова, списки Known и Unknown, привязки Anki, уровень.
2. **Проекция** `card_states` — состояние каждой карточки: разобрана ли, раздел при каждом пороге. Только она нужна ревью для счётчиков, порядка и фокуса.
3. **Outbox.** Код, который меняет источник правды, в той же транзакции пишет событие «что изменилось» в таблицу `card_events`. Изменение без события невозможно: они коммитятся вместе.
4. **Обработка синхронная.** Перед коммитом транзакции события этой транзакции применяются к проекции. Ответ на нажатие уже содержит новые разделы, и позже ничего не меняется.
5. Проекцию можно **пересобрать с нуля**; при старте приложения она пересобирается. Воркер **периодически сверяет** её с полным расчётом.

Фронт получает и рисует только видимое: окно карточек и главу текста.

## Термины

- **Карточка** — фраза, которую показывает ревью (`phrases.shown_by` задан).
- **Порог** — порог частотности, одно из 8 значений `THRESHOLD_STEPS`: 2.5, 3.0, …, 5.5 или «выключен».
- **Новизна слова** (`Newness`) — правило `is_new` без порога:
  - `ALWAYS` — в Unknown, изучается или ждёт экспорта;
  - `IF_RARE` — содержательное, выше уровня и не в Known: новое, если реже порога;
  - `NEVER` — не новое.
- **Входы раздела** — таблицы, из которых он считается: `phrases`, `candidates`, `known_words`, `unknown_words`, `anki_synced_cards`, `settings.cefr_level`. Кроме того, время — таймер Anki.

## Domain: одно правило

- `THRESHOLD_STEPS` и `step_index(threshold)`. Калибратор и ручные ключи порога берут шаги отсюда; порог вне набора — ошибка.
- `newness(word, vocabulary, user_level) -> Newness`. `is_new` выражается через неё.
- `PhraseNewness` — число новых слов фразы (разных лемм) для каждого шага, собранное из новизны её слов.
- `section_of`, `open_section` и сортировки переписаны через `PhraseNewness` и Protocol `SortFacts`. Поведение не меняется. Ни SQL, ни фронт правил не повторяют.

## События

| Событие | Кто создаёт | Что пересчитать |
|---|---|---|
| `LemmaChanged(lemma)` | запись списков Known/Unknown, решения по слову, привязки Anki, статус и факты слова | карточки этой леммы во всех источниках и фразы, где она стоит |
| `PhraseChanged(phrase_id)` | создание, правка текста, показ, удаление фразы | эту фразу; лемму её слова |
| `SourceChanged(source_id, lemmas)` | обработка, Update, Re-cut, удаление источника. Леммы собираются до удаления: каскад базы удалит слова молча | все карточки источника; переданные леммы |
| `EverythingChanged` | смена уровня | всё; на экране лоадер, ~2 с на 50 тыс. карточек |

**Кто создаёт события — репозитории, а не use case'ы.** Событие пишет каждый метод записи репозитория, который меняет входную таблицу или удаляет её родителя (источник). Use case'у ничего вызывать не нужно. Новый use case получает события бесплатно, потому что пишет через те же репозитории.

Репозитории-писатели (по коду, а не по памяти):
- `sqla_occurrence_repository`;
- `rebuild_plan_writer`;
- `sqla_word_state_repository`;
- `sqla_candidate_repository`;
- `sqla_known_word_repository`;
- `sqla_unknown_word_repository`;
- `sqla_anki_sync_repository`;
- `sqla_source_repository` (удаление);
- репозиторий настроек.

## Что гарантирует, что событие не забыто

1. **Писать во входные таблицы могут только репозитории-писатели.** Архитектурный тест сканирует код. Конструктор модели, `insert`/`update`/`delete` модели, `session.delete` и присваивание полей входной модели разрешены только в этих модулях. Новое место записи в обход — тест красный.
2. **Каждый метод записи этих репозиториев создаёт событие.** Тест перебирает методы портов-писателей по интроспекции и вызывает каждый. Метод, после которого в `card_events` пусто, роняет тест. Добавленный в порт метод записи без события тоже ронят. Исключение — только явный список «не меняет вход» с причиной.
3. **Каскады базы.** Тест падает, если у входной таблицы появляется `ON DELETE CASCADE` от таблицы, чей репозиторий не создаёт `SourceChanged`. Сейчас это только `sources`.
4. **Дифференциальный тест.**
   - Случайные последовательности реальных use case'ов: решения и отмены, списки, синхронизация, удаление источника, Rebuild, Re-cut, polish, граница, смена уровня, сдвиг часов через таймер.
   - После каждой операции проекция сравнивается с полным расчётом нынешним кодом (`LiveCardStates`): состояния, счётчики и порядок трёх сортировок.
   - `hypothesis`, фиксированный seed, < 10 с.
5. **Сверка в работе.** Воркер раз в час сравнивает проекцию с `LiveCardStates`; при расхождении — ERROR в `make logs`. `make card-states-check` выводит diff по запросу.

Пункты 1–3 ловят забытое событие при разработке, пункты 4–5 — ошибку в самой проекции.

## Обработка

`CardStateProjection` (application) — единственный, кто пишет в `card_states`. Порт хранилища внедряется только в него; архитектурный тест это проверяет.

- **Применение событий.** Обработчик `before_commit` сессии SQLAlchemy (infrastructure, один на фабрику сессий) перед любым коммитом вызывает `apply_pending()`: события этой транзакции применяются и удаляются. Это работает одинаково для 44 коммитов в роутах, unit of work и воркера, и ничего нигде вызывать не надо.
- **Пересчёт по событию.** Правилами из domain:
  - `LemmaChanged` — новизна строк леммы в `phrase_words`, затем `PhraseNewness` и разделы фраз, где она стоит;
  - у карточек самой леммы — `is_done` и `wants_generation`.
- **Таймер Anki** — единственный вход без записи. Перед чтением проекции леммы, чей 30-дневный таймер истёк с прошлой проверки, получают `LemmaChanged`. Граница — `known_on` из domain.
- **Пересборка с нуля** при старте app: ~2 с на 50 тыс., ~4 с на 121 тыс. карточек. Смена правил и миграции этим покрыты, без версий и хешей. Воркер стартует после app.
- **Идемпотентность.** Пересчёт по одному событию дважды даёт тот же результат.

Во время пересборки при старте запросы ждут её окончания; на экране лоадер.

## Хранилище

**`card_states`** — одна строка на карточку.

| Колонка | Что это |
|---|---|
| `phrase_id` | PK |
| `source_id`, `word_id` | отбор по набору и группировка по слову |
| `is_done`, `wants_generation` | из `card_view` |
| `open_sections` | 8 букв: открытый раздел при каждом шаге порога |
| `new_counts` | 8 чисел для сортировки |
| `revision` | номер последнего изменения (для обновления окна) |

Индексы: `(source_id, revision)`, `(source_id, is_done, open_sections)`, `(word_id)`. Раздел карточки — `section(is_done, open)` из domain. SQL лишь выбирает букву по `step_index` и группирует.

**`phrase_words`** — слова фраз-карточек: `phrase_id`, `position`, `lemma` (lower-case), `zipf`, `content`, `level`, `newness`. Индекс `(lemma)`.

**`card_events`** — outbox: `id`, `kind`, `key`. Пуст после каждого коммита.

**`card_removals`** — `phrase_id`, `revision`: удалённые карточки за 7 дней, для обновления окна.

Рост базы на всём Worm: 173 → 239 МБ (+38%).

## Чтение и API

| Запрос | Ответ |
|---|---|
| `GET /api/review?scope&sort&around` | шапка; снимок порядка (id, раздел, `is_done`) и его ревизия; окно; начальный фокус |
| `POST /api/review/refresh {scope, since, window_ids, pressed_id?}` | шапка; изменения с `since`; окно; `next_focus_id`; `snapshot_stale` |
| `POST /api/review/cards {ids}` | полные данные карточек |
| `GET /api/review/documents?scope` | список глав |
| `GET /api/review/documents/{source_id}` | текст главы и подсветки (`phrase_id`, `is_done`) |

- **Шапка** — как сейчас в `ReviewDTO`: прогресс, `learn_count`, статус, `busy`, а также `ai_unavailable` по всему набору.
- **Изменения с `since`:**
  - у бывших в снимке — только `is_done` (раздел не меняется до перезагрузки, как сейчас);
  - новые карточки — с `after_id` по текущему порядку;
  - удалённые;
  - `changed_sources` — главы со сменившимися подсветками.
- **`next_focus_id`** считает backend по нынешнему правилу `nextFocus`; данные этой карточки приходят в том же ответе.
- **`snapshot_stale`** — снимок пора перестроить: закончилась busy-операция или `since` старше хранимых удалений.
- **Окно** — показанный префикс («Show more») плюс текущая карточка с соседями ±N. Данные окна перечитываются целиком.

Снимок строит backend для всех сортировок, включая chronological.

## Фронт

- Одна обёртка `mutate → refresh` для всех действий вместо 13 ручных `loadCandidates`.
- Фронт применяет ответ и ничего не вычисляет:
  - снимок и изменения;
  - фокус;
  - шапку;
  - перечитывание глав.
- `currentId` меняется, когда данные карточки уже в окне.
- Опрос не стартует, пока не закончился предыдущий.
- Текст справа — глава текущей карточки и глава правки границы; скрытая панель убирается из разметки.

## Замеры прототипа (весь Worm, 121 тыс. карточек)

| | Сейчас | С решением |
|---|---|---|
| Пересчёт после нажатия, 99% слов | ~20 с на всё | 11–30 мс |
| Пересчёт для самых частых слов книги (до 2558 карточек) | ~20 с | до ~130 мс |
| Само решение (`decide`) | ~20 мс | ~20 мс |
| Счётчики | — | 26 мс |
| Открытие ревью (снимок и сортировка) | ~25 с | ~0,25 с |
| Пересборка проекции | — | ~4 с |

Проекция совпала с текущим правилом на 121 тыс. карточек после 11 настоящих нажатий, расхождений 0.
