# Ревью коллекции размером с книгу

## Проблема

Каждое действие в ревью пересчитывает и передаёт весь набор карточек, а фронт рисует текст всех глав. На всём Worm (121 тыс. карточек) нажатие стоит ~20 с, открытие ревью — ~25 с. Время растёт линейно с размером набора.

Чтобы нажатие стоило миллисекунды, состояние карточек (раздел, разобрана ли) нужно хранить готовым и пересчитывать только у затронутых карточек. Это надёжно, только если данные и пути записи устроены по принципам ниже.

## Основа: модель статусов от 19.10.2026

Модель «слово / фраза / показана» и таблицы решений согласованы раньше (`words-phrases-rebuild.md`, коммит `c1768fff`). Они остаются, кроме изменений, перечисленных в этой спеке.

- **Слово** (`candidates`) — лемма в источнике и её факты.
- **Фраза** (`phrases`) — место в тексте и всё, что к нему относится: текст, выбор на карточке, перевод, правки. Rebuild обновляет фразу на месте, а не пересоздаёт (`rebuild_plan_writer.py:73–150`).
- **Показана** — отметка `shown_by`.
- **Статус слова вычисляется** из фактов: выбор на карточке, отметки Known и Unknown, привязки Anki.

## 1. Правило статусов (Макс, 21.10.2026)

Видимый статус слова один: `нет`, `учу`, `в Anki`, `знаю` или `не знаю`. Факты «решение учить» и «не знаю» не сосуществуют:

| Действие | Если у леммы | Результат |
|---|---|---|
| Learn или Cloze | отметка «не знаю» | решение «учу», отметка «не знаю» снимается |
| Known | отметка «не знаю» | «знаю», отметка снимается (так уже сейчас) |
| отметка «не знаю» (жалоба, Settings) | решение «учу» или «в Anki» | ничего: «учу» уже значит «не знаю» |
| отметка «не знаю» | «знаю» | снятие Known каскадом (так уже сейчас) |
| отмена Learn | — | статус «нет»; прежняя отметка «не знаю» не возвращается |

Почему так:
- Отметка «не знаю» на слове, которое уже учишь, ничего нового не сообщает. Если бы она снимала «учу», жалоба на другую фразу молча стирала бы решение, очередь экспорта и привязку во всех источниках.
- Факты не сосуществуют, поэтому маска «Unknown скрывает таймер» (`card_choice.py:210`, `lemma_knowledge.py:51,75–77`, `vocabulary.py:15–17`) становится мёртвым кодом и удаляется.
- Приоритет 19.10 «Unknown > Known > Learning > Learn» больше не нужен.

Видимое следствие одно: после отмены Learn слово из «не знаю» возвращается в «нет».

Переходы записываются строками таблиц решений, как все остальные (принцип 19.10):
- Learn и Cloze на лемме с «не знаю» получают эффект `FORGET_UNKNOWN`;
- отметка «не знаю» получает таблицу U* по ключу (выбор, вид заметки, reads_known).

Это касается и нажатий, которые система делает за пользователя (Saved phrases, Replace with example).

## 2. Таблицы: три исправления

| Сейчас | Нарушение | Станет |
|---|---|---|
| `candidates.status` | хранимая копия вычисляемого статуса, с отдельным писателем (`sqla_word_state_repository.py:89–94`) | удаляется |
| `known_words`, `unknown_words` | две таблицы для взаимоисключающих отметок; регистр лемм разный | `word_marks(lemma PK lower-case, mark known/unknown, created_at)` и `known_pos(lemma FK, pos)` |
| `anki_synced_cards.card_choice` | зеркало выбора, переписывается при каждом сохранении слова (`sqla_word_state_repository.py:77–88`) | пусто, пока карточка жива; записывается один раз, когда карточка или источник исчезают |

**Кто читает статус после удаления `candidates.status`.**
- Правила (`awaiting_export`, P6, `reads_known`) читают факты: `phrases.choice` и активные привязки. Проекцию они не читают, иначе получился бы цикл.
- Проекцию читает только интерфейс.

**Отметки.**
- Схема гарантирует, что у леммы не бывает одновременно known и unknown.
- Решение против отметки и инвариант AK (решение Known ⇒ отметка known) держит владелец, `UserVocabulary` вместе с таблицами решений.
- Пустой `pos` в `known_pos` значит «любая часть речи» и поглощает остальные. Удаление в Settings идёт по паре (лемма, pos).

**`card_choice`.** Колонка нужна только сиротским правилам O0–O2 (`decision_rules.py:549`). Её пишет репозиторий Anki, по явному вызову из сценариев удаления карточки или источника, до удаления. `bind()` её больше не пишет.

## 3. Принципы

1. **У каждого факта один владелец.** Владелец — это порт репозитория в domain, а не таблица целиком:

   | Факт | Владелец |
   |---|---|
   | выбор на карточке | `WordStateRepository` |
   | текст, показ, нарезка, Rebuild | `OccurrenceRepository` (запись Rebuild — его часть) |
   | факты слова, удаление слов | `CandidateRepository` |
   | отметки | `UserVocabulary` |
   | привязки | `AnkiSyncRepository` |
   | результаты генерации и картинки | их репозитории |

   Каскады базы, которые меняют факты (удаление источника, `SET NULL` в привязках), считаются записью владельца удаления, `SourceRepository`, и он создаёт событие.
2. **Вычисляемое — только в проекции.** Её читает интерфейс, правила её не читают.
3. **Транзакция — только через `SqlaUnitOfWork.write()`, по построению.**
   - Session не выходит за пределы persistence и DI.
   - Роуты, use case'ы и воркер получают Unit of Work, а не сессию.
   - `session_scope` и отдельная фабрика сессий (`container.py:389, 915`) уходят.
   - Вложенный `write()` — ошибка; `rollback` сбрасывает события.
4. **Правила — только в domain.** SQL выбирает и сортирует готовые значения, фронт ничего не вычисляет.
5. **Время меняет состояние явной записью** через порт `Clock`.

## 4. События

События — value objects в domain. Порт `ChangeRecorder` (domain) внедряется владельцам через DI. Запись события — часть контракта метода записи, поэтому фейковые реализации в тестах обязаны её соблюдать.

| Событие | Владелец |
|---|---|
| `DecisionChanged(lemma)` | `WordStateRepository` |
| `PhraseChanged(phrase_id)` | `OccurrenceRepository` |
| `WordsChanged(source_id, lemmas)` | `CandidateRepository` |
| `SourceDeleted(source_id, lemmas)` — леммы собираются до удаления | `SourceRepository` |
| `MarkChanged(lemma)` | `UserVocabulary` |
| `BindingChanged(lemma)` | `AnkiSyncRepository` |
| `CardContentChanged(phrase_id)`, `WordContentChanged(word_id)` | генерация, картинки, правки |
| `LevelChanged` | настройки |

Каждый коммит `write()`, включая промежуточные коммиты в use case'ах, перед коммитом передаёт события проектору `CardStateProjector` (application). Проектор:
1. заново читает снимок знаний, в своей транзакции;
2. берёт `now` из того же снимка;
3. пересчитывает затронутое правилами domain;
4. увеличивает ревизию из счётчика в БД.

Лемма из события доходит до карточек во всех источниках и до индекса `phrase_words`. Ответ use case'а читается после применения проекции.

**Почему явные события, а не триггеры или отслеживание сессии.**
- Триггеры держат логику в базе и ломают миграции.
- Отслеживание сессии неявно и не видит массовых запросов.
- Явное событие видно в коде, а мест его создания — по одному на метод записи владельца.

## 5. Проекция

| Таблица | Что хранит |
|---|---|
| `lemma_states` | `lemma`, видимый статус, `changes_at` — когда статус изменится по времени (Anki + 30 дней) |
| `card_states` | `phrase_id`, `source_id`, `word_id`, `lemma`, `is_done`, `wants_generation`, решение здесь или в другом источнике; раздел и число новых слов при каждом из 8 шагов порога (`THRESHOLD_STEPS`); ключи сортировки; `changes_at`; `revision` |
| `phrase_words` | `WITHOUT ROWID`, PK `(lemma, phrase_id)`, индекс по `phrase_id` |

Индекс `(source_id, is_done)` для счётчиков, частичный индекс по `changes_at`, индекс по `revision`.

- **Время.** В воркере отдельная asyncio-задача, независимая от очереди задач, раз в минуту обычным `write()` пересчитывает строки с `changes_at <= now`. Чтение ничего не пишет.
- **Пересборка с нуля при каждом запуске.** Одной транзакцией `BEGIN IMMEDIATE`, до приёма запросов (~4 с на всю книгу). Это перестройка кэша после смены кода правил и миграций, а не починка багов: баги ловит дифференциальный тест до вливания. `make up` и `make up-worktree` останавливают воркер до старта app.
- **`LevelChanged`** — полный пересчёт в запросе настроек (~4 с), на экране лоадер.
- **Журнал SQLite — WAL**, `synchronous=NORMAL`. Тяжёлые операции идут одной транзакцией на источник, а не на коллекцию.

## 6. Гарантии

1. **Дифференциальный тест** в `make test`.
   - Генератор сценариев строится по списку пишущих методов портов: новый метод без сценария роняет тест.
   - Сценарии включают общие леммы в разных источниках, удаление источника и сдвиг часов.
   - После каждого шага проекция совпадает с полным расчётом: статусы, разделы, счётчики, порядок каждой сортировки.
2. **Тест портов:** каждый пишущий метод порта-владельца создаёт событие.
3. **Тест пути коммита:**
   - Session, `commit()`, `begin()` и `sessionmaker(` есть только в persistence;
   - вложенный `write()` падает.
4. **`make card-states-check`** — для разработчика: расхождения проекции с полным расчётом, без исправлений.

`make test` обязателен перед каждым вливанием.

## 7. API и фронт

- **Ревью открывается с `review_id`** (scope и сортировка). Сервер держит порядок этого ревью в памяти: id, позиция и раздел на момент открытия. `is_done` всегда свежий, как сейчас в `keepLayout`.
- **Мутации принимают `review_id`.** Ответ — ревизия, изменения и следующая карточка для фокуса. Правило фокуса сравнивает состояние карточки до и после этой мутации, как сейчас `focusAfterPress`.
- **Изменения** — по ревизии карточки. Ревизия покрывает и статус, и содержимое: перевод, polish, озвучка, картинка слова. Сервер отдаёт полные карточки по загруженным id и подсветки по загруженным абзацам.
- **Строки списка готовит сервер:** карточки и строки разделов со счётчиками, по открытым разделам клиента. Раздел текущей карточки сервер раскрывает сам; в порядке текста разделов нет. Позиция и prev/next — по видимому списку.
- **Новые карточки:**
  - после Rebuild, Update или Re-cut — за ближайшей уже стоявшей, со свежим разделом;
  - из примера — на место заменённой;
  - добавленное слово становится фокусом;
  - исчезнувшая карточка уходит, фокус переходит к следующей.
- **Ленивая подгрузка при прокрутке** для списка и для текста, в обе стороны.
  - Переход к дальней карточке (клик, ссылка, следующая в другой главе) запрашивает окно вокруг неё. Клиент держит загруженные участки и заглушки между ними.
  - Текст идёт кусками по абзацам, с абсолютным номером блока. Граница куска не делит блок; выделение больше одного блока backend и так отклоняет.
  - В коллекции сначала приходит оглавление документов.
  - Правка границы открывает текст на позиции фразы.
  - Загруженное не выгружается.
- **После перезапуска сервера** ревью переоткрывается на текущей карточке.
- **Шапка:** прогресс, статус, `busy`, «AI недоступен» по всему набору.
- Уходят `initially_shown_candidates`, `useShownCandidates` и «Show more».

## 8. Миграция данных

- Резервная копия перед миграцией делается автоматически (`database.py:67–73`). `downgrade` — `NotImplementedError`, как в `0048`/`0049`.
- `candidates.status` удаляется нативным `ALTER TABLE DROP COLUMN`, без пересоздания таблицы.
- **Отметки** сливаются в `word_marks` и `known_pos` по `lower(lemma)`. `created_at` — максимум из слитых строк.
- **Конфликты решаются правилом из раздела 1, без выдуманных дат:**
  - «не знаю» вместе с Learn — остаётся «учу»;
  - known вместе с unknown — побеждает более поздний `created_at`;
  - два решения по одной лемме — побеждает решение с активной привязкой, иначе с более поздним `studied_at`, иначе с меньшим id.
- Каждое изменение пишется в `data/migration-<номер>.log`.
- Проверка — на копии dev-базы и на копии с Worm; копии делаются через backup API.

## 10. Этапы

Каждый этап — своя ветка, все существующие тесты зелёные.

1. Unit of Work по построению: Session только в persistence, единый `write()`; тест пути коммита.
2. Владельцы фактов как порты, `ChangeRecorder`; тест портов.
3. Domain:
   - правило статусов из раздела 1 строками таблиц;
   - `THRESHOLD_STEPS`;
   - новизна слова без порога;
   - раздел при каждом шаге.
4. Таблицы: `word_marks` и `known_pos`, удаление `candidates.status`, `card_choice` как факт исчезновения; миграция с логом.
5. Проекция, проектор, задача времени, пересборка при запуске, WAL, дифференциальный тест, `make card-states-check`.
6. API и фронт ревью: `review_id`, окно, строки списка с сервера, ленивая подгрузка списка.
7. Текст справа: ленивая подгрузка по абзацам.
