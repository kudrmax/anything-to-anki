Модель документа источника

Два слоя. Reader формата знает, как прочитать файл, и отдаёт контент одного из четырёх видов: текст, книга, субтитры, песня. KindHandler вида знает, что продукт делает с таким контентом, и создаёт источники. Итог — документ из блоков.

Версия 20

00Принцип

  • Приложение работает только с документом. Вход превращается в документ, после этого оригинал забывается.
  • Всё, что нужно для работы, делается при построении документа: очистка текста, разворот сленга (wanna → want to). Дальше текст документа не меняется.
  • Экран источника, поиск фраз и target'ов, время фраз, контекст для жалоб и полировки, сортировка — всё берётся из документа.
  • Если внешней библиотеке нужен плоский текст (spaCy), адаптер склеивает документ в текст и переводит результат обратно в позиции документа. Остальное приложение об этом не знает.

02Вход

SourceInput = PastedText { text }
            | LocalFile  { path, subtitles_path? }
            | Url        { url }

Других видов входа нет. Формат и вид контента определяются, а не задаются. subtitles_path — внешний .srt к видеофайлу; если он задан, дорожку субтитров не спрашиваем.

Через эту загрузку создаётся только контент. Topic создаётся своим CreateTopicUseCase (пишет topic_query), Saved phrases — как сейчас; документа у них нет.

03Формат и Reader

Формат — как устроен файл. На каждый формат один Reader. Reader знает только свой формат и отдаёт Content.

FormatКак определяетсяВопросы Reader'аОтдаёт
PLAINвставленный текст без разметки; .txt и другой текстовый файл с неизвестным расширением«текст или песня»Text или Song
MARKDOWN.md, .markdown; вставленный текст с разметкой markdown (заголовки #, списки, **, ссылки)«текст или песня»Text или Song
HTML.html, .htm; вставленный текст с html-тегами«текст или песня»Text или Song
EPUB.epub—Book
SRT (VTT — потом)расширение; вставленный текст со строками таймкодов -->. VTT — потом, как fb2—Subtitles без видео
VIDEO_FILE.mp4, .mkv, .avi, .movдорожка субтитров (если их несколько и не задан subtitles_path) и аудиодорожка (если их несколько) — одним окном, как сейчасSubtitles с видео и выбранной аудиодорожкой
YOUTUBEссылка на YouTube—Subtitles, видео скачивается потом
  • Вставленный текст определяется по содержимому: строки таймкодов → субтитры, разметка markdown → markdown, html-теги → html, иначе plain.
  • «Текст или песня» спрашивается для любого текстового входа, по умолчанию «текст». Не спрашивается только там, где вид однозначен по устройству файла: epub — книга; субтитры, видео, YouTube — субтитры.
  • При ответе «песня» любой текстовый Reader делает строку документа из каждой строки входа (в html — из строк через <br>) и не разбирает списки и заголовки: строки песни на «-», «1.», «#» остаются строками.
  • subtitles_path у файла, который не видео, — ошибка.

Ошибки при добавлении (как сейчас, за каждой отвечает свой Reader)

  • Файл не найден; бинарный файл неизвестного формата — «формат не поддерживается».
  • Пустой вставленный текст, пустой .srt; документ без текста — ошибка уже при добавлении, а не при обработке.
  • Видео без субтитров и без внешнего .srt — «приложите .srt».
  • YouTube без субтитров — сообщение «субтитры недоступны»; ссылка не на YouTube — «ссылка не поддерживается».
  • Нечитаемая книга — ошибка чтения книги.

04Content и KindHandler

Content — что это за контент для продукта. Видов четыре, на каждый один KindHandler с продуктовой логикой этого вида. Он не знает, из какого формата пришёл контент.

Content   = Text      { title, document }
          | Book      { title, chapters: [Chapter { title, document }] }
          | Subtitles { title, document, video: VideoRef? }
          | Song      { title, document }

VideoRef  = LocalVideo   { path, audio_track? }
          | YouTubeVideo { url }               видео скачивается потом, по кнопке
KindВопросы KindHandler'аЧто создаёт
TEXT—один источник
BOOKделить ли на главы — с превью: сколько глав, их будущие названия и число слов в каждой; одна глава — без вопросаисточник на главу в коллекции с названием книги и названиями глав по шаблону; или один источник
SUBTITLES—один источник; с видео — кадры и аудио для карточек
SONG—один источник
  • Добавить fb2: Fb2Reader, который отдаёт Book. Главы, коллекция и названия работают сразу.
  • Добавить логику только для книг: правка BookHandler, работает для всех форматов книг.
  • Kind хранится у источника и заменяет нынешний content_type. Продуктовые ветвления в остальном коде (TTS, кадры и аудио, полировка фраз) идут по kind и признаку «у источника есть видео».
  • «Есть видео» — у Subtitles есть video. Для YouTube это ссылка, скачанного файла может ещё не быть, но источник с самого начала ведёт себя как видео. format на источник ставит AddSourceUseCase.

Поведение по виду и видео (как сейчас)

Все места, где код сейчас ветвится по input_method/content_type (источник, обработка, генерация, медиа, скачивание и очистка YouTube-видео, статистика хранилища, Topic, Saved phrases, фронт), переходят на kind, role и «есть видео». DTO источника отдаёт эти три поля; фронт берёт иконки и подписи из них. То, что касается только YouTube (хранение пути скачанного видео, его скачивание и удаление), ветвится по format == YOUTUBE.

05Document

Document   { blocks: [Heading | Paragraph | ListItem] }

Heading    { level: 1..6, text }            в позиции у заголовка line = 0
Paragraph  { lines: [Line], mode: FLOW | LINES }
ListItem   { lines: [Line], ordered, depth }

Line       { text, start_ms?, end_ms? }
  • Line — строка. У прозы в абзаце одна строка, у песни — строчка куплета, у субтитров — реплика с началом и концом.
  • mode: FLOW — предложение продолжается со строки на строку (проза, субтитры). LINES — каждая строка сама по себе (песни, стихи). Ставит Reader.
  • Текст строк уже очищен и со развёрнутым сленгом. Это один общий шаг в AddSourceUseCase сразу после чтения, а не копия в каждом Reader'е.
  • Субтитры — один абзац FLOW со всеми репликами по порядку; строки — строки реплик по порядку, у каждой время своей реплики: фраза не переходит между блоками, а предложение в субтитрах переходит между репликами. В «бегущих» автосубтитрах YouTube первая строка реплики повторяет последнюю строку предыдущей — Reader субтитров удаляет такой повтор до сборки строк.
  • Книга целиком (без разбиения) — один документ из блоков всех глав подряд.
  • Блок появляется, только если он есть в файле. Строки и блоки, ставшие пустыми после нормализации («[Chorus]», ♪), выкидываются (у субтитров вместе со временем); пустой документ — ошибка при добавлении.

06Порты и use case'ы

FormatDetector
  detect(input) → Format

Reader                                    один на Format
  questions(input) → [Question]           что нужно, чтобы прочитать файл
  read(input, answers) → Content

KindHandler                               один на Kind
  questions(content) → [Question]         продуктовые вопросы
  create(content, answers) → SourcesCreated

DocumentRepository
  save(source_id, document) / get(source_id) → Document

Question  { id, prompt, options: [{ id, label, details? }], default }
          details — пояснение к варианту, например список глав с числом слов
Answers   { question_id → option_id }
AddSourceUseCase
  execute(input, title?, answers?) → QuestionsRequired { questions }
                           | SourcesCreated    { source_ids, collection_id? }

  1. format  = detector.detect(input)
  2. reader  = readers[format];  вопросы reader'а без ответов → QuestionsRequired
  3. content = reader.read(input, answers)
  4. content = нормализация текста (очистка, разворот сленга)
  5. handler = handlers[content.kind];  вопросы handler'а без ответов → QuestionsRequired
  6. handler.create(content, answers)

DetectFormatUseCase
  execute(input) → { format, kind_label }      подпись под полем ввода («Book · epub»)
  • AddSourceUseCase заменяет нынешние CreateSource, CreateSourceFromUrl, CreateBookSources и отдельный выбор дорожек.
  • Фронт показывает вопросы одним общим окном и вызывает use case ещё раз с ответами. Он не знает, кто спрашивает.
  • Вопрос задаётся, только если вариантов больше одного. Одна глава, одна дорожка — без вопроса, как сейчас.
  • Каждый вызов начинается с нуля и получает все накопленные ответы. Id вопросов уникальны (video.subtitle_track, video.audio_track, book.split, text.kind); неизвестный ответ — ошибка.
  • title — своё название источника. Не задано — название из файла (заголовок книги, имя файла, имя видео), как сейчас.
  • ProcessSourceUseCase читает Document вместо raw_text; парсеры в пайплайне не нужны.
  • GetSourceDocumentUseCase отдаёт документ и позиции фраз для экрана источника.
  • Подсказку о типе файла под полем считает backend (DetectFormatUseCase), а не фронт.
  • Реестры Reader'ов и KindHandler'ов собираются в container.py.

07Нарезка фраз

  • Фраза не переходит из блока в блок. Заголовок — отдельная фраза.
  • FLOW: строки склеиваются, предложение может занимать несколько строк.
  • LINES: конец строки — конец фразы, если следующая строка не продолжает предложение.
  • Фразы и target'ы ищутся в документе. Пайплайн текст документа не меняет.
  • У кандидата хранится позиция фразы и позиция target'а внутри неё: { block, start_line, start_char, end_line, end_char }, символы считаются в code points (фронт переводит в свои единицы сам). По ним подсвечиваются фраза и target на экране. Если подсветки пересекаются, backend сам выбирает, какую показать (как сейчас: точное совпадение важнее), и присылает непересекающиеся позиции.
  • context_fragment остаётся полем кандидата и заполняется куском документа по позиции при создании; его используют правки, синхронизация с Anki, кэш обогащения.
  • Время фразы — от начала первой до конца последней строки, которые она занимает. Считается при обработке, как сейчас.
  • Контекст для жалоб и полировки — соседний текст документа вокруг фразы, тот же, что пользователь видит на экране. Хронологическая сортировка — порядок позиций в документе; кандидаты без позиции — в конце.
  • Topic ищет фразы в документах других источников через DocumentRepository: внутри каждого блока, с тем же правилом выбора короткого предложения, что сейчас.

Правки фраз пользователем — логика не меняется

  • Изменить границы фразы выделением, добавить слово выделением: как сейчас, но фронт присылает позицию выделения, а текст фразы backend берёт куском документа. Правка идёт через use case (сейчас роут пишет в базу напрямую). Ничего не пересчитывается. Выделение через границу блока — ошибка «фраза должна быть в пределах одного абзаца». Позицию target'а при добавлении слова считает backend.
  • Замена фразы примером: как сейчас; позиция пустая, потому что примера нет в документе.
  • Полировка: как сейчас; позиция не меняется.
  • Время фразы считается при обработке, кадр и аудио — при генерации медиа и по кнопке «Regenerate media», как сейчас. Меняется только то, откуда берётся время: из строк по позиции фразы, а не поиском текста в субтитрах.

Что меняется в пайплайне

  • Очистка и разворот сленга уходят из обработки в построение документа.
  • Адаптер spaCy склеивает документ (строки FLOW через пробел, LINES через перенос, блоки через пустую строку; строке LINES, которая закончила предложение, только для spaCy дописывается точка — во фразу она не попадает), держит карту смещений и возвращает позиции слов в документе (у слова появляется смещение символа).
  • Парсер песен больше не дописывает точки. Решение «строка закончила предложение» адаптер принимает предварительным проходом по строкам той же логикой, что сейчас (она смотрит на разбор пар строк), и передаёт spaCy готовые границы предложений.
  • Фраза — непрерывный кусок документа (так и сейчас на практике). Target — от первого до последнего своего слова (покрывает разорванный фразовый глагол).
  • Стадии обработки «очистка источника» и «сопоставление таймкодов» исчезают, вместе с их подписями во фронте.
  • Поиск таймкодов по тексту и парсеры в пайплайне удаляются; перенарезка медиа берёт время из строк документа.
  • Кэш обогащения при переобработке сравнивает фразы без учёта пробелов: фраза, вырезанная заново, может отличаться от старой только пробелами. Иначе переобработка старого источника потеряла бы значения, медиа, озвучку и картинки.

09Хранение

  • source_documents — новая таблица: source_id, документ в JSON. Список источников его не загружает.
  • sources: input_method и content_type заменяются на format, kind и role (контент, Topic, Saved phrases). Видео — как сейчас, video_path и audio_track_index.
  • candidates: добавляются позиция фразы и позиция target'а. Пустые у Saved phrases и кандидатов Topic: у них нет документа.
  • raw_text и cleaned_text больше не нужны; превью в списке источников берётся из начала документа.
  • topic_query — запрос Topic (сейчас лежит в raw_text); заполнен только у роли Topic, генерация target'ов Topic читает его.
  • Название вставленного текста по умолчанию — начало документа; число вхождений при добавлении слова считается по документу.

10Миграция

Меняется только форма хранения старых данных; логика их получения не применяется заново. После миграции на проде те же источники, те же фразы, те же числа слов и фраз, те же статусы, полировки и ручные правки, тот же вид экрана. Новая логика (раздел 12) работает только для новых источников.

  1. Документ старого обработанного источника — один абзац FLOW, строки которого — строки текущего cleaned_text как есть: без повторной очистки, разворота сленга и пересчёта границ. Точки в песнях остаются. Так экран и рисует его сейчас: одиночный перенос склеивается пробелом. Пустых строк в старом cleaned_text нет, поэтому блок один.
  2. Время строк у видео: сохранённый SRT разбирается заново и построчно выравнивается со строками cleaned_text; строка получает время своей реплики. Проверка — время фраз, выведенное из строк, совпадает с уже сохранённым у кандидатов.
  3. Кандидаты не пересоздаются. Позиция фразы — первое вхождение без учёта пробелов и регистра; позиция target'а — тем же правилом, каким его сейчас подсвечивает фронт (включая фразовые глаголы). При повторах — первое вхождение, как сейчас. context_fragment, polished_fragment, ручные правки, медиа, озвучка, картинки, статусы не меняются. Фраза, заменённая примером, остаётся без позиции.
  4. Необработанные источники (кандидатов нет) получают документ новыми Reader'ами из сохранённого текста: книги — Plain-reader'ом с видом Book (epub не хранится), markdown — Markdown, субтитры и видео — Srt, вставленный текст — Plain, песня — Plain как Song.
  5. Topic и Saved phrases: запрос Topic переносится в topic_query, документов у них нет.

Как выполняется

  • Миграции запускаются при старте приложения, поэтому перенос — ревизия Alembic между ревизией «добавить» и ревизией «удалить». Код переноса написан прямо в ревизии под реальные данные прода и не импортирует Reader'ы и пайплайн приложения.
  • Прогон на копии прод-базы во временной папке (не в ./data dev-копии) → сверка «до и после» по каждому источнику: число кандидатов, слов и фраз; статусы, полировки, ручные правки; склеенный для экрана текст документа совпадает с тем, что экран показывает сейчас; кусок документа по позиции совпадает с фразой с точностью до пробелов; подсвеченный target совпадает с нынешней подсветкой; хронологический порядок тот же; без позиции только замены примером. Расхождений быть не должно.
  • Перед обновлением прода — копия app.db. После успешного переноса тело ревизии переноса очищается.
  • Следствие решения: у старых книг абзацев нет, и после их переобработки фразы по-прежнему могут проходить через заголовки. Новые книги этого не имеют.

11Текущие возможности сохраняются

Всё, что есть сейчас, остаётся; меняется только устройство внутри.

  • Своё название источника на любом пути; без него — автоматическое.
  • Выбор файла через «Choose…» и перетаскивание в macOS-приложении, в том числе видео вместе с .srt; подсказка с типом файла под полем.
  • Видео: внешний .srt или встроенные субтитры; выбор дорожки субтитров и аудио, если их несколько.
  • YouTube: субтитры сразу, видео скачивается отдельной кнопкой.
  • Книга: окно разбиения на главы с числом слов, коллекция с названием книги, шаблон названий глав в настройках, повторно добавленная книга попадает в ту же коллекцию, главы в списке по порядку.
  • Песня: выбор «текст или песня», построчная нарезка фраз.
  • Пути, скопированные из терминала (в кавычках, с экранированием); ошибки для отсутствующего и бинарного файла; файлы в UTF-16 и cp1252.
  • Topic и Phrase — как сейчас.
  • Обработка, переобработка, удаление источника. Переобработка пересчитывает фразы и target'ы по документу с текущими настройками и, как сейчас, сбрасывает полировку и ручные правки фраз; значения, медиа, озвучка и картинки восстанавливаются из кэша.
  • Правка границ фразы выделением, добавление слова выделением, замена фразы примером, полировка.
  • Сообщения об ошибках при добавлении — см. раздел 03.

13Этапы

Всё в одной ветке, в master вливается целиком.

  1. Document, Content, SourceInput, Question в domain; DocumentRepository и таблица.
  2. Reader'ы всех форматов, KindHandler'ы, AddSourceUseCase, DetectFormatUseCase, CreateTopicUseCase.
  3. Черновик ревизии переноса на данных dev: какие документы получаются у старых источников.
  4. Пайплайн на документе: адаптер spaCy с позициями, фразы по блокам и режимам, время из строк, кэш переобработки без учёта пробелов.
  5. Перевод всех ветвлений на kind, role, «есть видео», format для YouTube.
  6. Фронт: экран рисует блоки, правки выделением по позициям, одно поле ввода, общее окно вопросов.
  7. Ревизия переноса под данные прода, прогон и сверка на копии прод-базы.
  8. Удаление старого пайплайна и старых колонок.

Проверка при разработке: разовый отчёт, который прогоняет одни и те же тексты через старый и новый пайплайн и показывает расхождения target'ов, фраз и времени для новых источников. Старый пайплайн удаляется только после этого отчёта. Часть расхождений ожидаема (раздел 12); остальные разбираются до вливания.
