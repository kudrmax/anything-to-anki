# Review at Book Scale — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** нажатие в ревью коллекции размером с книгу стоит десятки миллисекунд, а состояние карточек всегда верно.

**Architecture:** вычисляемое состояние карточек хранится в проекции. Её обновляет проектор по явным событиям владельцев фактов перед каждым коммитом единственного Unit of Work. Фронт получает окно карточек и текст кусками при прокрутке.

**Tech Stack:** Python 3.12, SQLAlchemy 2, SQLite, Alembic, FastAPI, hypothesis (новая dev-зависимость), React + TypeScript.

**Spec:** `docs/specs/review-at-book-scale.md` (коммит `9357da32`).

## Как устроен этот план

План общий: в нём все этапы, их результат, интерфейсы и проверка. Пошагово (TDD) расписан только этап 1. Пошаговый план каждого следующего этапа пишется в его начале, в этот же файл: интерфейсы этапов 3–7 зависят от кода, который появится в этапах 1–2.

Каждый этап — своя ветка от `perf/collection-review` и своё вливание. Перед каждым вливанием:
- `make lint`, `make typecheck`, `make test`;
- для фронта — `npm run lint` и `npm run build`.

Всё должно быть зелёным.

## Global Constraints

- Правила только в domain. SQL выбирает и сортирует готовые значения, фронт ничего не вычисляет.
- `mypy --strict`, без `Any` без комментария; `dataclass(frozen)` в domain, pydantic в DTO.
- Схема — только Alembic. `downgrade` у миграций с потерей данных — `NotImplementedError`.
- Процессы — только через make. Проверка — в worktree на копии базы, prod не трогать.
- Коммиты: conventional commits, без упоминания Claude.
- Порог частотности ∈ `THRESHOLD_STEPS` = (2.5, 3.0, 3.5, 4.0, 4.5, 5.0, 5.5, None).

## Review Focus

1. **Удаление источника, в котором было Learn**: в других источниках карточки этой леммы снова открыты, а фразы с ней пересчитаны. Тест — в этапе 5, сценарий дифференциального теста.
2. **Rebuild большой главы, пока открыто ревью**: ревью не падает с `database is locked`, нажатие ждёт не дольше одной транзакции источника. Тест — в этапе 8, замер.
3. **Жалоба с «не знаю» на слово, которое учишь**: ничего не меняется. Тест — в этапе 3, строка таблицы U*.
4. **Переход к карточке в далёкой главе по клику в тексте**: открывается окно вокруг неё, без загрузки всего, что перед ней. Тест — в этапе 6.
5. **Перезапуск сервера при открытом ревью**: ревью переоткрывается на текущей карточке, без ошибки. Тест — в этапе 6.

### Этап 6 пошагово

Ветка `perf/review-window` от `perf/collection-review`. Миграции: `0059` (что считает ✨: открытые разделы, сделанное генерацией, тайминги клипа; покрывающие индексы шапки и ✨) и `0060` (что очередь держит для каждой карточки, по видам генерации). Текст справа остаётся целым (этап 7): меняются только отметки разобранных фраз в нём.

Решения при исполнении:
- **Чтение проекции — свой порт `CardStateQuery`**, отдельный от пишущего `CardStateStore`. Его получают только экраны: шапка, порядок ревью, обновления, подсветки, прогресс источников. Архитектурный тест держит список читателей. Почему: принцип 2 — проекцию читает интерфейс, правила её не читают.
- **Ключи сортировки в `card_states` не копируются** (в спеке, §5, они есть). Порядок читает строки проекции вместе с фактами слова и местом фразы одним запросом. Почему: это факты слова, у них уже есть владелец.
- **`sort_cards` принимает лёгкую строку `OrderedCard`** (протокол `SortableCard`), а не только `ReviewCard`. Почему: на открытии книги нельзя строить 121 тыс. `ReviewCard`.
- **Порядок открытого ревью держит `ReviewOrderStore`** в памяти app: порт в domain, реализация в infrastructure, не больше `REVIEWS_KEPT = 16` ревью, вытесняется самое давнее. Почему: спека держит порядок в памяти; предел не даёт вкладкам копить память.
- **Сервер помнит, какие строки он отдал ревью.** Полные карточки в обновлении — только по ним. Разобранность для текста справа — по всем изменившимся карточкам набора (`done`). Почему: «полные карточки по загруженным id» без списка id в каждом запросе; текст пока целый.
- **Один ответ на всё — `ReviewUpdateDTO`**: открытие, окно, раздел, опрос и каждая мутация ревью. Клиент шлёт `since` (своя ревизия) и `current`, ответ доводит его до `revision`. Почему: одна обёртка на фронте; гонка опроса и нажатия безопасна.
- **Открытые разделы хранит ревью на сервере.** Какие разделы свёрнуты по умолчанию — константа domain, а не фронта. Почему: строки разделов со счётчиками строит сервер (§7).
- **Ревизия покрывает и задания.** `SqlaJobRepository` при смене статуса задания пишет `CardContentChanged`/`WordContentChanged`, `SqlaCardReportRepository` — при жалобе. Почему: карточка показывает `polish_status`, ошибку генерации и `reported`; без событий опрос их не увидит.
- **✨-счётчики (`/review/generation`) и тексты (`/review/documents`) считаются как сейчас**, но первая карточка их не ждёт. Их время на всей книге меряется в 6.5 и уходит Максу. Почему: в §7 их нет; тексты — этап 7.

Решения о поведении, которые спека оставляет открытыми (Максу на вето):
1. После перезапуска сервера или вытеснения ревью открывается заново на текущей карточке и с теми же открытыми разделами, но в свежем порядке: разобранное с прошлого открытия уходит в Reviewed. Нажатие, которое сервер отклонил из-за истёкшего ревью (до записи), фронт повторяет один раз после переоткрытия. Цена: раскладка перестраивается один раз, как сейчас при перезагрузке страницы.
2. Исчезла текущая карточка — фокус на следующую под ней в видимом списке, без неё — на ту, что над ней. Цена: только само правило.
3. «AI недоступен» по набору — флаг шапки: проваленная генерация значения показанной фразы с ошибкой блокировки региона. Сбой AI-ручки при блокировке региона отвечает 503, остальные сбои AI — 502 (сейчас тоже 503). Цена: другие сбои AI меняют код ответа; фронт перестаёт искать маркер в тексте ошибки.
4. Старые `GET /api/review` и `GET /api/review/candidates` удаляются. Интеграционные тесты читают список через новое окно. Цена: правка ~12 тестовых файлов.
5. Экран источников берёт прогресс из той же проекции, что и шапка. Цена: нет; одно место вместо двух.

- **Task 6.1 — порт чтения и шапка из проекции.** `CardStateQuery` (`revision`, `section_tallies`, `done_of_sources`) и архитектурный тест читателей. `ReviewHeader` (прогресс, статус, `learn_count`, `busy`, `ai_unavailable`); `ReviewProgress` экрана источников — по счётчикам проекции. `is_done` у подсветок текста; `AIUnavailableError` → 503. Тесты: в дифференциальном тесте шапка и прогресс каждого источника и коллекции равны живому расчёту; замер счётчиков на всей книге.

### Этап 7 пошагово

Ветка `perf/text-chunks` от `perf/collection-review` после вливания этапа 6. Миграций нет.

Сейчас `GET /api/review/documents` отдаёт целиком документы всех источников набора с подсветками всех показанных фраз. На всём Worm (305 глав, 121 тыс. карточек) это примерно 37 МБ JSON:
- текст — около 10 МБ;
- подсветки — около 21 МБ (по ~175 байт на каждую);
- обёртка блоков — около 6 МБ.

Сервер ради этого читает и раскладывает 305 документов. Фронт рисует весь текст сразу. Перечитывает всё после правки границы, после добавления слова и каждые 3 с, пока источник занят. Точные время и размер на всей книге есть в отчёте 6.5.

Документ источника пишет только `SourceWriter`, при создании источника, и дальше он не меняется: Rebuild, Update и Re-cut его только читают. Поэтому номер блока постоянен, текст куска никогда не устаревает, а меняются только подсветки.

Решения при исполнении:
- **Кусок — целые блоки, пока их текст не больше `TEXT_CHUNK_CHARS = 20_000` символов; блок длиннее — кусок сам по себе.** Границы кусков считает domain из документа, номер блока абсолютный. Почему: граница не делит блок (§7); глава книги — 2–3 запроса по ~70 КБ.
- **Кусок — чтение открытого ревью, как строки:** `GET /api/review/{review_id}/text/{source_id}?block=N` (`-1` — последний блок) отвечает `ReviewUpdateDTO` с полем `text`. Почему: одна обёртка на фронте; ревизия ответа сравнивает «разобрана» из куска с `done` из других ответов.
- **Место фразы в куске выбирается по `phrases.block`** — блоку ключа, где начинается target. Он равен блоку позиции фразы. Документ читается один раз на запрос. Почему: не разбирать все фразы источника ради одного куска.
- **Перекрытие подсветок решается внутри блока**, ведь позиция фразы лежит в одном блоке. Поэтому кусок даёт ровно те подсветки, что и целый документ. Правило переезжает из use case'а в domain (`text_marks.py`). Почему: принцип 4.
- **Номер пункта списка даёт сервер** (`BlockDTO.number`). Почему: фронт считал его по соседним пунктам, а в куске их может не быть.
- **Оглавление:** `GET /api/review/{review_id}/contents` — источники набора с документом, в порядке набора, с заголовком и `size_hint`. `size_hint` — длина хранимого документа, она нужна только для высоты заглушки. Каждый ответ ревью несёт `contents_version`, которая растёт при смене состава источников набора. Почему: размер известен без чтения документов; версия не теряется, даже если ответ отброшен как устаревший.
- **Сервер помнит отданные куски и места фраз в них** (`ServedText` в `OpenReview`). Место фразы — позиция, target, CEFR, phrasal. Изменения несут подсветки куска целиком (`highlights`), только если у изменившейся карточки место стало другим, она появилась в отданном куске или ушла из него. Почему: §7, «подсветки по загруженным абзацам»; при этом нажатие на частой лемме не пересчитывает ни одного куска, а разобранность идёт в `done`, как в этапе 6.
- **Переоткрытое ревью получает загруженные куски в `OpenReviewRequest.text_chunks`** и отвечает их свежими подсветками. Почему: загруженное не выгружается, а новое ревью о нём не знает.
- **«Разобрана» в тексте** — более новое по ревизии из двух значений: из подсветки куска и из `done`. Почему: это механическое сравнение, без правил; `forgetDone` и перечитывание документов уходят.

Решения о поведении, которые спека оставляет открытыми (Максу на вето):
1. Текст появляется после открытия ревью: открытие → оглавление → кусок у текущей карточки. Параллельно открытию он больше не грузится. Цена: на маленьком источнике текст приходит на два коротких запроса позже первой карточки. На книге — на секунды раньше, чем сейчас.
2. Прокрутка к фразе текущей карточки плавная, если её кусок уже нарисован и между ним и экраном нет заглушки. Иначе прокрутка мгновенная, как в списке (6.4). Цена: переход к фразе в дальней главе — мгновенный.
3. Свёрнутый документ ничего не грузит, и текущая карточка в нём текст не прокручивает (так и сейчас). Правка границы раскрывает документ своей фразы и открывает текст на её блоке. У фразы без места (пример) текст остаётся там, где был. Если у её источника ещё ничего не загружено, грузится первый кусок. Цена: место для примера ищут прокруткой, как сейчас.
4. Источник ушёл из набора — его куски уходят вместе с ним. Новый источник появляется в оглавлении заглушкой. Цена: нет; сейчас то же делает перечитывание документов.
5. Подсветки меняются по ответам ревью. После замены примером или удаления карточки её подсветка уходит сразу, а перекрытая ею становится видна. Сейчас это происходит только при следующем перечитывании. Цена: нет.
6. Сервер держит места фраз отданных кусков, около 250 байт на фразу. Если клиент прочитал всю книгу, ревью держит около 30 МБ; ревью не больше `REVIEWS_KEPT` = 16. Цена: память растёт только при такой прокрутке; этап 8 меряет её на всей книге.

Для пользователя не меняется:
- порядок и заголовки документов, их сворачивание;
- вид подсветок, клик по подсветке (`goTo`, окно вокруг дальней карточки);

- номера и маркеры списков.
