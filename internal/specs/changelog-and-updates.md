# Changelog и обновления

Решение согласовано с Максом 28.10.2026.

## Зачем

Приложением пользуются другие люди: ставят его через `git clone` и `make setup`. Сейчас они не знают, что вышло что-то новое, и обновляются вручную через `git pull`. Нужно, чтобы пользователь видел, что вышла новая версия и что в ней, и обновлялся одной кнопкой. Макс обновляет свой prod так же, как все пользователи.

Не цели: автообновление без нажатия, каналы beta/stable, обновление словарей (`anything-to-anki-dicts`).

## Релиз

- Релиз выпускается только по команде Макса («выпускай релиз»). Мерж в master — ещё не релиз.
- Версия по SemVer, единственный источник — `version` в корневом `pyproject.toml`. Backend читает этот файл при старте. Версию в `backend/pyproject.toml` не трогаем, она ни на что не влияет. *Моё решение:* номер выбирает агент: есть `feat:` с прошлого релиза — растёт минорная цифра, только `fix:` — патч.
- Релиз = коммит в master с новой версией и записью в `CHANGELOG.md` + тег `vX.Y.Z` + GitHub Release с тем же текстом.
- Текущая версия приложения — `1.0.0` (решение Макса). Первый релиз — `v1.0.0`, сразу после того как эта фича влита в master: иначе в первом релизе не было бы обновления кнопкой.

### Запись в CHANGELOG.md

Формат как у [Obsidian](https://obsidian.md/changelog/), на английском (это пользовательская документация):

```markdown
## 0.3.0 — 2026-11-02

One sentence: what this release is about.

### Bulk add from a folder
Text about the big feature.
![](docs/images/changelog/0.3.0/bulk-add.png)

### New
- …
### Improvements
- …
### No longer broken
- …
```

- Крупные фичи — отдельными разделами со своим заголовком, перед New. Пустые разделы не пишутся.
- Пункты — человеческим языком для пользователя, без внутренних изменений (рефакторинг, тесты, миграции, docs).
- Скриншотов максимум: у каждой крупной фичи и у заметных пунктов. На скриншоте стрелка или рамка показывает, куда смотреть.
- Картинки лежат в `docs/images/changelog/<версия>/`, путь в Markdown — от корня репозитория.

### Скилл `release`

Весь процесс — project-скилл `.claude/skills/release/SKILL.md`:

1. Проверить, что master чистый и совпадает с `origin/master`.
2. Собрать коммиты с прошлого тега, разложить по разделам, написать текст.
3. Снять скриншоты в **dev-копии** (уже запущенной, `make up` там же) — все фичи релиза по очереди за один проход. Браузер headless, панель, которую смотрит Макс, не трогать. Стрелки и рамки рисует сам скилл; способ — на усмотрение строителя, но одинаковый от релиза к релизу (например, SVG-оверлей, вставленный в страницу перед снимком).
4. Поднять версию, дописать `CHANGELOG.md`, закоммитить `chore: release vX.Y.Z`, поставить тег, запушить master и тег, создать GitHub Release (`gh release create`) с телом записи. Картинки в теле релиза — абсолютные ссылки на `raw.githubusercontent.com/.../vX.Y.Z/...`.
5. *Моё решение:* скилл публикует сразу, без отдельного согласования текста — Макс может поправить релиз на GitHub и в следующем коммите.

## Что видит пользователь

### Доступна новая версия

- Backend проверяет последний релиз не чаще раза в сутки — при запросе фронта, результат (номер версии и время проверки) кэшируется.
- Если релиз новее текущей версии — в шапке появляется тихий индикатор «Update available» (мелкий приглушённый текст, без цвета и колец). Точное место показать реальным скриншотом до реализации.
- Клик открывает **попап обновления**: записи всех версий новее текущей (в том же виде, что changelog) и кнопка **Update**.
- Попап закрывается крестиком. Индикатор остаётся, пока пользователь не обновится.

### Проверить обновления вручную

- **Сайт:** в настройках кнопка **Check for updates** рядом с **Changelog**.
- **macOS-приложение:** дополнительно пункт **Check for Updates…** в меню приложения сразу после **Settings…**, как в стандартных macOS-приложениях. Он работает через тот же мост, что Settings… (событие в WebView), и открывает то же, что кнопка на сайте.
- Проверка идёт сразу, мимо суточного кэша. Есть новая версия — открывается попап обновления. Нет — «You're on the latest version (X.Y.Z)».

### Обновление

1. **Update** → backend запускает `make update` отдельным процессом, который переживает остановку самого backend.
2. Страница показывает «Updating…» поверх всего и опрашивает сервер.
3. Сервер вернулся с новой версией → страница перезагружается (как сейчас при новой сборке, `client_build.py` / `clientBuild.ts`) → открывается попап «Что нового».
4. Ошибка → попап показывает текст ошибки, последние строки `.logs/update.log` и команду `make update` с кнопкой «Copy». Копия остаётся на старой версии (см. ниже).

### Что нового

- Появляется при первом открытии после обновления: все версии, вышедшие после той, что пользователь видел последней. Закрывается крестиком и больше не появляется.
- Какую версию пользователь уже видел, хранит backend (ключ в таблице настроек). На свежей установке попап не появляется: при первом старте backend просто записывает текущую версию как увиденную.
- **Changelog** в настройках открывает тот же попап со всей историей.

## make update

Одна команда, которой пользуются и кнопка, и терминал. Гарантии важнее удобства: копия после команды либо на новой версии и запущена, либо на старой и запущена.

1. Отказ, если в копии есть незакоммиченные правки отслеживаемых файлов (`data/`, `.env` в `.gitignore` и не мешают). Текст ошибки говорит, что сделать.
2. `git fetch --tags origin`. Если HEAD уже содержит последний тег релиза (`git merge-base --is-ancestor`) — «Already up to date», выход без изменений. Так dev и свежий `git clone` на master никогда не откатываются на старый тег.
3. Запомнить текущий HEAD, `make down`, снять копию базы через `DatabaseBackup`, `git checkout` последнего тега (detached HEAD).
4. `make setup-python` (зависимости из lock-файла). Фронт-зависимости и сборку фронта делает `make up`, миграции — старт backend.
5. Если в копии собрано macOS-приложение (бандл в `~/Applications` с `A2AProjectDir` этой копии) и код `frontends/macos` между старым и новым HEAD поменялся — `make app`.
6. `make up`.
7. Любой шаг после checkout упал → вернуть базу из копии шага 3 (миграции новой версии могли успеть пройти), `git checkout` запомненного HEAD, `make setup-python`, `make up`, выход с ошибкой. Лог всего — в `.logs/update.log`, его же показывает `make logs`.

Пока идёт обновление, сервер выключен, поэтому база между копией и откатом не меняется.

Во время долгой операции (замок `long_operation_lock`) **Update** отклоняется так же, как любая запись (423). *Моё решение, Макс может отменить.*

## macOS-приложение после обновления

- В `Info.plist` при сборке зашивается хэш дерева `frontends/macos` (`git rev-parse HEAD:frontends/macos`).
- Приложение сравнивает свой хэш с хэшем в `Info.plist` установленного бандла на диске — при каждой загрузке страницы. Отличается → баннер в окне «Restart to finish the update» с кнопкой **Restart**.
- **Restart** открывает новый бандл и закрывает текущий, **не** выполняя `make down` (серверы уже на новой версии). Владение серверами передаётся новому экземпляру (например, флагом запуска): как и сейчас, выход из приложения, которое запустило серверы, их останавливает.
- Пока `make update` перезапускает серверы, старый экземпляр не должен сам запускать `make up` по проверке здоровья: копия под замком `with_copy_lock`, но лишний запуск не нужен.
- Backend про macOS-приложение не знает: проверка целиком в Swift.

## Устройство (backend)

- Порт `ReleaseSource` (последний релиз и его записи changelog). *Моё решение:* адаптер работает через git, а не через GitHub API: `git fetch --tags origin`, последний тег `vX.Y.Z`, `CHANGELOG.md` и картинки — `git show <тег>:<путь>`. Так нет зависимости от API и лимитов, а обновление можно проверить на локальном bare-репозитории вместо настоящего GitHub.
- Порт `UpdateRunner` — адаптер запускает `make update` в каталоге копии отвязанным процессом.
- Парсер `CHANGELOG.md` → value objects (версия, дата, сводка, разделы, пункты, картинки). Один парсер для текущей версии и для будущей. Картинки обеих backend отдаёт сам (с диска или из git-объекта тега).
- Use cases: `CheckForUpdates` (с кэшем и без), `GetChangelog` (вся история / непросмотренное), `MarkChangelogSeen`, `StartUpdate`.
- `GET /api/version` — текущая версия, по ней фронт понимает, что сервер вернулся новым.
- Последняя проверка, её результат и увиденная версия — ключи таблицы настроек, без миграций схемы.

## Prod Макса

- Prod переходит на релизы: обновляется кнопкой, как у всех. При первом релизе агент переключает prod-копию на тег (`git checkout vX.Y.Z`, только git-операция).
- «Вливай» больше не обновляет prod: мерж в master и push. Prod получает изменения со следующим релизом.
- Dev остаётся на master и всегда не старше последнего релиза, поэтому индикатор там не появляется, а `make update` отвечает «Already up to date». Код про dev/prod не знает.
- В той же ветке обновить раздел «Репозитории» и «Dev/Prod» в `CLAUDE.md`: prod обновляется кнопкой или `make update`, не `git pull`. Память агента про «вливай» обновить после мержа.

## Проверки

- Тесты парсера на записях со всеми разделами, без разделов, с картинками.
- Тест `make update`: падение после миграций возвращает копию на старый HEAD со старой базой и запускает её; HEAD на master впереди тега — ничего не меняется.
- Тест use cases: свежая установка не показывает «Что нового»; пропущенные версии показываются все.
- Ручной прогон: `make update` для worktree не делаем. Отдельный клон в scratchpad со своим `.env` (свой `PORT`), `origin` — локальный bare-репозиторий, в нём фейковый тег с записью changelog. Индикатор → попап → Update → перезагрузка → «Что нового», плюс откат при сломанном теге. Скриншоты индикатора и попапов — до реализации UI.
